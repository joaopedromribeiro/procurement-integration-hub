## Recommended alternatives understood

Managed RAP fits greenfield custom persistence; unmanaged behavior is useful when existing application logic owns saving. Synchronous REST is simpler for the first round trip; messaging improves outage tolerance while adding ordering and recovery concerns. TypeScript supports maintainability in CAP; JavaScript is viable for a smaller service. Graphical CI mapping makes the learning transformation visible; scripts should have a specific reason to exist.

These are project decisions to validate, not claims that one pattern is universally superior.

## Phase 2.4C — header TotalAmount runtime-verified

The business invariant is header TotalAmount = sum of current item TotalAmount values. Item create/input changes and item delete are child-level triggers because those operations change the aggregate. The implementation identifies affected roots through the composition associations and reads sibling inputs through EML in local mode, so uncommitted transactional values participate.

RAP does not guarantee ordering among determinations. The create/update method therefore derives each rounded item total from Quantity × NetPrice and builds the root sum from those same derived values; it does not wait for another determination's TotalAmount update. Changed item totals and affected root totals are then written in one local-mode EML request. This makes the calculation repeatable and independent of determination order.

The debugger established a second deletion lesson: RAP used different handler ME instances for precheck and determination. A populated instance attribute therefore did not survive, and READ TABLE returned sy-subrc 4. Handler instance lifetime is not transaction lifetime; replacing it with CLASS-DATA would introduce unmanaged shared state. The correction uses local variables and a read-only lookup of the committed item's immutable parent UUID, then EML for current sibling inputs and the root update. This respects the save boundary for previously committed active items, but cannot identify a newly created/uncommitted deleted item. That limitation is explicit; a broader solution needs parent identity in the key or verified target-supported change/before-image access. Error messages from determinations alone do not enforce a save veto.

## Phase 2.7A — Root business action `submit`, runtime-verified

A business action is not a technical operation. `removeItem` maintains an aggregate; `submit` changes what the order *is* in the procurement lifecycle. Both are instance-bound root actions delegating authorization to root update, but their preconditions differ in kind: `removeItem` asks whether an item belongs to this instance, while `submit` asks whether this instance is in a state that may advance.

Active-only is a deliberate boundary, not a limitation of the framework. A technical draft is an editing session, so submitting one would persist a lifecycle decision over data that has not necessarily passed any `on save` validation. The supported path is framework `Activate`, which runs `Prepare` and therefore all three validations, followed by `submit` on the resulting active instance. The handler enforces this by rejecting `%tky-%is_draft = mk-on` before it reads anything, rather than by a BDEF clause whose syntax is unconfirmed on this target. Handler-side enforcement also survives any future projection that exposes the action.

Preconditions must not restate business rules that already have owners. Every committed active root has passed `validateSupplier`; every committed active item has passed `validateQuantity` and `validateNetPrice`; a value cannot change without re-triggering its own validation. Re-reading Supplier, Quantity and NetPrice inside `submit` would create a second copy of each rule that could silently drift from the first. The action therefore checks only what no validation covers: draft flag, business `Status`, and the existence of at least one item. The at-least-one-item check reads the live composition through `BY \_Items`, so an order emptied by `removeItem` is rejected at submission time rather than at creation time.

Requiring `Status = 'DRAFT'` rather than merely "not already SUBMITTED" makes the transition explicit and closed. A second `submit` is rejected with a specific message instead of quietly succeeding, and every future status added by 2.7B onward is excluded by default rather than by omission.

Deferring is a design decision worth recording. Submission is the natural allocation point for `PurchaseOrderNumber`, but no number-range facility is confirmed on this target, and inventing a placeholder identity would create migration debt. Likewise, making commercial fields read-only after `SUBMITTED` requires instance feature control whose generated components vary by release, and it would change the runtime-verified `removeItem` path. Both are separated into their own subphases with their own evidence. The honest consequence, recorded rather than hidden, was that a submitted order remained editable at this checkpoint; Phase 2.7B closed that, and `PurchaseOrderNumber` is still deferred.

Action rejections carry `%op-%action-submit` and a message, never an `%element` marker; element markers belong to validations, which point at a field. An action is not a nested database transaction, so every rejection leaves the buffer untouched and the caller must roll back. The console tests assert the FAILED table and the buffer contents directly instead of inferring a veto from REPORTED.

The learner's SAP run confirms all of this. The active transition reached `SUBMITTED` with the buffered total unchanged at 1500, committed with `sy-subrc` 0 and persisted, while `PurchaseOrderNumber` stayed initial. Each rejection returned its exact text and changed nothing: `Only orders in status DRAFT can be submitted.` on re-submit, `Submit requires at least one item.` on an order with no items, and `Submit is not allowed on a draft instance.` on both a buffer-only and a saved technical draft, whose totals stayed 1500 and 1900. The Phase 2.5 validations and the Phase 2.6 active and draft removal tests still pass, so the new action did not disturb the earlier baseline.

The run settles four declaration questions for this target: a parameterless `action ( authorization : update ) submit;` activates under `strict ( 2 )` in a `with draft` behavior definition; the generated handler receives the complete root `%tky` including `%is_draft`; `%op-%action-submit` exists in the generated root FAILED and REPORTED structures; and `EXECUTE submit FROM VALUE #( ( %tky = ... ) )` is accepted for an action with no parameter. Each action contributes its own `%op` component, so this is now evidence for `submit` specifically, not an inference from `removeItem`.

The identical message on both draft cases is the useful detail. A buffer-only draft and a saved draft differ in persistence but not in `%is_draft`, and the guard reads the flag rather than the storage, so both are rejected the same way and neither is mutated. Rejecting before the first read also means a draft call performs no EML at all.

Shortening the three asserted texts to 46 characters or fewer before the run was the right call: they were returned in full. The Phase 2.6 limit still stands as a constraint to design within, since a 53-character text was truncated to 50 on this target and the console tests compare returned text exactly.

Runtime verification covers the transition and its rejections, and nothing more. `PurchaseOrderNumber` was still unallocated, and post-submission editing was still open at this checkpoint. Verifying an action does not verify the restrictions that ought to surround it; Phase 2.7B supplies those separately, with its own evidence.

## Phase 2.7B — Post-submission immutability through prechecks, runtime-verified

The probe round mattered more than the implementation. Four questions were answered with target evidence before a line of enforcement was written, and two of the answers collapsed whole branches of the design.

**Precheck is an operation option, not a derived type.** Autocomplete for `STRUCTURE FOR` and `TABLE FOR` proposes no type named "precheck" on this target. The enforcement is declared as `update ( precheck )` on root and item and `create ( precheck )` inside the `_Items` association, and ADT generates `METHODS precheck_update FOR PRECHECK IMPORTING entities FOR UPDATE purchaseorder`, its item twin, and `METHODS precheck_cba_items FOR PRECHECK IMPORTING entities FOR CREATE purchaseorder\_items`. Every signature was generated by ADT and used verbatim. Guessing any of them would have failed, exactly as guessing `%tky` for the framework draft actions failed earlier.

**`%control` is what makes the rule safe.** The `FOR UPDATE` line type exposes `%cid_ref`, `%control`, `%data`, `%is_draft`, `%key`, `%pky`, `%tky` and the entity fields, with an individual `%control` flag per field. Scoping the check to the five user-writable root fields and the seven user-writable item fields means the rule cannot fire on `submit`'s own `Status` write or on the `TotalAmount` writes of the determinations. A blanket "no update when SUBMITTED" rule would have broken Phase 2.7A on its own transition. The field list, not the operation, is the safety mechanism.

**An unresolved question stopped mattering once the design was scoped correctly.** Whether a precheck executes for an `IN LOCAL MODE` request was never determined. It did not need to be: under either answer the outcome is the same, because the only local-mode writes this behavior pool performs touch readonly fields that no guarded list contains. Designing so that an open question becomes irrelevant is cheaper than answering it, and the full regression passing unchanged confirmed it empirically.

**Two probe results decided the draft design.** `Edit` on a `SUBMITTED` active order succeeds and the resulting technical draft carries `Status = SUBMITTED`, so the ordinary rules guard it through `%tky` with no extra logic. And `submit` on an active instance is refused by the framework with `%FAIL = LOCKED` while a saved draft of it exists. Together these mean a draft coexisting with a submitted active instance can only have been created after submission, so no active-counterpart lookup and no `Edit` gate are needed. Both were earlier assumed to be necessary; both were dropped on evidence.

**The limits of that evidence are part of it.** The `LOCKED` result is single-user, from one console flow — a concurrency outcome, not a business rule, and no rule was weakened because of it. `Activate` over a `SUBMITTED` instance was never reached and is not claimed. Neither observation generalizes beyond SAP_BASIS 758 SP01 / S4CORE 108 SP01.

**Mechanisms rejected, and why.** Instance feature control is advisory for UI rendering and `IN LOCAL MODE` bypasses it, so it could never be the enforcement layer; it stays available as optional UX. A validation-on-save backstop would have added no coverage, fired late, and risked interfering with the root-delete cascade through a delete-triggered validation. Authorization was the wrong tool entirely: `SUBMITTED` is instance state, not a permission.

**Root `DELETE` stays allowed, and the reason is concrete.** Removing a submitted order belongs to `cancel` in the documented lifecycle, and the Phase 2.7A regression deletes its own submitted fixture during cleanup. Blocking deletion here would have broken runtime-verified coverage in the same change that added enforcement. A half-rule that costs regression coverage is worse than a stated gap. Phase 2.7D-1 has since added `cancel` without touching `DELETE`, and the deletion policy became Phase 2.7D-2 for exactly the reason stated here: the teardown cost is real and deserves its own round.

The learner's SAP run verifies all six active rejections with persistence unchanged, root `DELETE` still working on a submitted order, a `DRAFT` control that still recalculates correctly, and a submitted-order draft that rejects both root and item changes. Every Phase 2.3–2.7A marker still printed, and no `STOP` marker appeared. `PurchaseOrderNumber` remains unallocated.

## Phase 2.7C — Approver decisions and the lifecycle invariant, runtime-verified

The transitions were the easy part. `approve` and `reject` reuse the `submit` shape exactly: draft-instance guard, local-mode status read, transition check, one local-mode update of readonly fields. `reject` adds a parameter through a new abstract entity, following the `ZJP_A_RemoveItem` pattern proven in Phase 2.6. Nothing about either action needed new target evidence, which is what a stable pattern is for.

**The real work was correcting the rule Phase 2.7B had written.** That subphase rejected changes when `Status = 'SUBMITTED'`, which was right while `SUBMITTED` was the only state after `DRAFT`. The moment `APPROVED` and `REJECTED` became reachable, an enumerated rule would have needed extending for every future state, and would have silently permitted edits to any state someone forgot to list. Inverting it — *editable only while `DRAFT`* — closes every state after `DRAFT` at once, including states not yet invented. A rule stated as an invariant survives the lifecycle growing; a rule stated as a list of forbidden states does not.

**Inverting a rule can break the cases the original accidentally allowed.** The naive inversion would reject instances whose `Status` is still `INITIAL`, because `initializeStatus` is a determination on modify and a newly created root can be readable before `DRAFT` is established. The old rule passed that case by accident; the new one had to pass it on purpose. The carve-out is written into the code as a transient framework accommodation, not folded into the business rule, and the comment says so — `INITIAL` is not an editable business state, it is the gap between creation and the determination that sets `DRAFT`. Documenting the distinction matters more than the two lines of code: a future reader must not read `INITIAL` as a lifecycle value.

**Eligibility outranks parameter validation.** The first version of `reject` checked the missing reason before reading the order, so a technical draft with an empty reason failed for the wrong reason and an already-approved order reported a missing parameter rather than an ineligible state. Reordered, the precedence is draft → unreadable → wrong status → missing parameter. A caller should learn the most fundamental reason their request is invalid, not the first one the code happened to test.

**Changing a rule means changing its messages, and messages are test contracts.** The four Phase 2.7B texts named `SUBMITTED` and became wrong the moment the rule generalized. Rewording them invalidated four exact-text assertions in a runtime-verified test class — and because only the production objects were activated at first, the stale SAP test classes reported `STOP: a submitted-order mutation was not rejected.` while every rejection in the log had actually fired correctly. The console output showed the right behavior and the wrong verdict. Test assertions that compare exact message text are precise but brittle; when a message changes, the class must be re-activated in the same round as the handler, or the evidence lies.

**On message length, a correction to earlier wording.** The target truncated one 53-character text to 50 characters on the Phase 2.6 path. That is empirical, target- and path-specific behavior. Earlier notes called it a 50-character limit, which overstates it: no documented universal limit was ever established. The durable practice is to keep messages short and verify the returned text in the console, not to trust a number.

The learner's SAP run verifies both transitions with persistence, `RejectionOrigin = APPROVER`, the reason stored verbatim, every re-decision and every commercial mutation on `APPROVED` and `REJECTED` rejected, a reason-less reject that wrote nothing, and a technical draft of a submitted order refusing updates and both decisions. `PurchaseOrderNumber` stayed initial throughout. Authorization remains the permissive study stub, so "approve" names a transition and not an access control — a distinction worth repeating wherever the word appears.

## Phase 2.7D-1 — The cancel action, runtime-verified

**The best measure of Phase 2.7C's invariant is how much code `CANCELLED` needed: none.** A fourth business state became reachable and not one precheck, not `removeItem`, not a single message text had to change. Commercial immutability, the four rejections and their exact texts all applied on the first run. Under the enumerated Phase 2.7B rule that named `SUBMITTED`, this subphase would have meant editing four handlers and re-verifying four assertions. A rule stated as an invariant pays out later, silently, in the work it does not create.

**An allow-list and a deny-list need different treatment of the same value.** The prechecks are deny-rules, so they need an explicit `INITIAL` carve-out or creation breaks. `cancel` is a positive allow-list of `DRAFT`, `SUBMITTED` and `APPROVED`, so `INITIAL` is excluded by construction — no carve-out, no comment, no risk of a reader mistaking it for a business state. Same value, same system, opposite handling, and both correct. The shape of a rule decides which cases need saying out loud.

**Not implementing a guard can be the more honest engineering choice.** The domain model says `APPROVED` may be cancelled only before delivery was requested. `IntegrationStatus` and `DeliveryId` exist in the model but are readonly and no Phase 2 handler writes them, so the condition is not merely false — it is unrepresentable as true. A guard would have been a tautology that could never fire, could never be tested negatively without forbidden direct SQL, and would read as enforcement in review while carrying no evidence. Writing it down as a Phase 5 obligation attached to `DeliveryIntent` is worth more than writing the branch. A defensive check you cannot exercise is not defense, it is decoration.

**Splitting a subphase is cheaper than an unattributable failure.** Phase 2.7D was planned as `cancel` plus the root `DELETE` narrowing. Narrowing deletion breaks the teardown of five fixtures that are deliberately terminal at cleanup — and there is no lawful managed replacement, because direct SQL is forbidden and `CANCELLED` would not be deletable either. Bundling a new transition with a teardown rewrite in two runtime-verified classes would have produced one activation round where a red console could mean either. The transition shipped alone, touching no existing test line: 609 insertions, zero deletions.

The learner's SAP run verifies all three cancellable sources with persistence and totals unchanged at 1500, `PurchaseOrderNumber` still initial, `REJECTED` refusing cancel while keeping `RejectionOrigin = APPROVER`, a `CANCELLED` order refusing re-cancel, `submit`, `approve`, `reject` and every commercial change, and a `SUBMITTED` technical draft refusing cancel. Root `DELETE` remains open at any status, which is a stated gap and not an oversight. Authorization is still the permissive study stub, so `cancel` names a transition and not an access control: any user may cancel any order.

## Phase 2.7E — PurchaseOrderNumber allocation on submit, runtime-verified

**Three documents said three different things, and nobody noticed until someone tried to implement.** The domain model said allocate on first active creation/save. The architecture register said determinations allocate display numbers. The Phase 2.7A guide and these notes said submission is the natural point. Each was written at a different time, each was reasonable alone, and the contradiction was invisible because the field was never implemented. A deferred decision does not stay neutral — it quietly accumulates inconsistent statements in every document that has to mention it. The investigation step that preceded this subphase existed precisely to surface that, and it was worth more than the code that followed.

**Submission beats save as the allocation point, for a reason that is about people rather than code.** A number drawn at creation is consumed by every abandoned draft. Submission is the first moment the order becomes a document other people cite in an email or a phone call, so that is when it earns an identity. The cost is that an order cancelled straight from `DRAFT` never receives a number — which is correct under the rule and had to be asserted deliberately, because it looks like a bug to anyone who assumes every persisted row has a display number.

**The target's own return type contradicts its own configuration.** `CL_NUMBERRANGE_RUNTIME` returns `NRLEVEL` as twenty digits while the configured `ZJP_PO` interval is eight. Taking the last eight characters is correct here and would be a silent corruption on a wider interval, so the handler checks that the leading twelve digits are zeros and fails the action otherwise. Under the configured interval that branch is unreachable, which is exactly why it costs nothing to keep: the guard is not there to fire, it is there so the truncation is a stated assumption rather than a hidden one.

**Deciding not to read a return code is also a decision.** The isolated probe returned a blank code, and SAP's documented non-blank values include a near-exhaustion warning where the number is still valid. Requesting `returncode` and treating any non-blank value as failure would refuse valid numbers as the interval fills; treating it as success would make the parameter decoration. With no runtime evidence for the non-blank paths, the honest choice was to request only `number`, rely on `CX_NUMBER_RANGES` for hard failures, and write the omission down as a reviewable decision rather than bury it.

**A number is drawn before the buffer update, so a failed save consumes it.** That gap is accepted by design — gaps are valid, numbers are never reset or reused — but it is worth naming, because the alternative people reach for is reusing the number, and that is how duplicate business identities get created.

**Optional parameters can carry a rule instead of a flag.** `expected_number` was added to two verification helpers with the semantics *initial means the row must still carry no number*. Every `DRAFT`-stage call site kept working untouched, and only the submitted-and-later sites had to pass anything. Choosing the default so that the common case needs no argument turned a twenty-call-site change into a seven-call-site change.

**The run confirms it, and the summary line nobody planned is the most useful output.** The final lifecycle table shows `SUP012 CANCELLED <initial>` beside five numbered orders. That blank is the rule working — a draft cancelled before submission never becomes a document anyone cites — but it is exactly the kind of thing that reads as a bug to the next person, which is why the regression asserts it on purpose and the documentation says so twice. The gap between `PO00000002` and `PO00000004` is the second such artifact: numbers are drawn before the buffer update, so a rolled-back request consumes one. Both were predicted before the run and both appeared; predicting an oddity beforehand is what turns it from a defect report into evidence.

**What the draft probe added was not planned at all.** A technical draft created from a `SUBMITTED` active order carried `PurchaseOrderNumber = PO00000009` along with `Status = SUBMITTED` and total 1500. Phase 2.7B had established that a draft inherits the business status; this extends it to the business identity. Nothing depends on that yet, but it is the kind of fact a Phase 3 OData client will meet on its first day.

**Paths that were never executed are still paths.** The two number-range exception branches and the wider-than-eight-digits guard did not fire in this run, and cannot be made to fire without breaking the configuration. They are compiler-accepted and reasoned, not runtime-exercised, and the documentation says so rather than letting a green console imply otherwise.

With this subphase Phase 2 is complete: the number range object, interval and 20-digit return behavior are learner-supplied target evidence, and the allocation, the formatting guard and the full regression all ran green on SAP.

## Phase 3.1 — OData V4 exposure, runtime-verified

**The best evidence that Phase 2 was layered correctly is how little Phase 3.1 had to do.** One ADT-generated projection behavior definition, one service definition, one binding. No handler changed, no rule moved, no test was touched, and the whole Phase 2 regression stayed valid without being re-run. A service layer that has to restate business rules is a sign the rules were in the wrong place to begin with; this one declares `use` and nothing else.

**The proof of that arrives as a string.** Approving an already-approved order over HTTP returns 400 with `Only submitted orders can be decided.` — byte-identical to the text the Phase 2.7C handler emits and the console test asserts. Two transports, one enforcement point. The same holds for `Only draft orders can be changed.` on a PATCH to a submitted order's draft.

**A compatibility adjustment that looked like debt turned out to be correct.** The child projection has no `provider contract transactional_query`, because the target compiler rejected that clause alongside `redirected to parent` back in Phase 1. Going into Phase 3 that was the highest-risk unknown — the one thing that might block a transactional service. It did not. Root contract plus redirected-to-parent child works here. The lesson is not that the worry was wasted; it is that naming the risk in advance made the answer cheap to obtain and impossible to miss.

**`Activate` and `submit` are different events, and OData shows it plainly.** A created order activates into business `DRAFT` with a blank number, and only `submit` returns `PO00000010`. Anyone watching the HTTP traffic can see that leaving the editing session is not the same as becoming a business document. The Phase 2.7E rule was argued on paper; here it is observable from outside the system.

**`Edit` succeeding on a submitted order still reads like a hole, and still is not one.** The draft is created, inherits `Status = SUBMITTED` and `PurchaseOrderNumber = PO00000010`, and refuses the first content change. Phase 2.7B established the mechanism; Phase 3.1 adds that the number is inherited too. It is worth saying out loud in every document that touches it, because the first reaction to "Edit returned 201" is always that something is wrong.

**The environment had the last word on publishing.** Client 100 is a Customizing client, so ADT refused to publish locally and the service group went through `/IWFND/V4_ADMIN`. No amount of correct modelling avoids that, and it is the kind of detail that costs an afternoon if it is not written down.

**Metadata can advertise more than the rules permit.** `__OperationControl` reports bound actions as available on orders whose lifecycle would reject them. That is a UX gap, not a rule defect — the handlers still return 400 — and the remedy, dynamic feature control, is deliberately not being reached for. Phase 2.7B already settled that feature control is advisory and bypassed by `IN LOCAL MODE`, so it can improve what a UI offers but can never be the thing that enforces. Implementing it unscoped would blur exactly the line this project has been careful to keep sharp.

`OptimisticConcurrency` now appears in the metadata, which makes a stale-ETag conflict reachable for the first time in the project. Nothing exercised one, so nothing is claimed; it stays open as OI-13.

## Phase 3.2 — UI annotations, runtime-verified

**An annotation placed three phases ago did the work.** `TotalAmount` renders as EUR in the Fiori List Report with no currency annotation anywhere in the metadata extension. `@Semantics.amount.currencyCode: 'Currency'` was put on the base view in Phase 1 for correctness reasons that had nothing to do with a UI, and it propagates through the projection, into OData, and out to Fiori on its own. Semantic annotations are not decoration on the data layer; they are the thing that lets every layer above stop re-stating what a field means.

**The ADT skeleton was placeholders all the way down, exactly as suspected.** `@Metadata.layer: layer` and `element_name` are literal placeholder tokens, not values. Autocomplete supplied the real set — `#CORE`, `#CUSTOMER`, `#INDUSTRY`, `#LOCALIZATION`, `#PARTNER` — and `#CUSTOMER` activated. Refusing to guess cost one lookup; guessing would have cost an activation failure and a wrong line in the repository.

**Activating a metadata extension refreshes `$metadata` without republishing the binding.** On this target that is worth more than it sounds: publishing needed `/IWFND/V4_ADMIN` because client 100 is a Customizing client, so a per-change republish would have made annotation work slow enough to discourage iteration. Establishing this early is what makes it reasonable to switch from one-annotation-at-a-time to activating the extension as a coherent unit.

**The Object Page title is the identity split made visible.** Before `@UI.headerInfo` existed, Fiori titled the page with `PurchaseOrderUUID`. Afterwards it shows `PO00000002`. Phase 2.7E argued on paper that the UUID is the technical key a client addresses while the number is what a person recognises; a UI with no annotations shows what happens when nothing tells the presentation layer which of the two a human should see.

**Restraint is a design decision that has to be made deliberately, because the default is clutter.** The root projection exposes twenty-four elements. Nine of them — `SupplierName`, `SupplierResponse`, `EstimatedDeliveryDate`, `IntegrationStatus`, `OrderRevision` and the four `LastError*` fields — are never written by any Phase 2 code and would render as permanently empty boxes. Annotating everything available would have produced a form that teaches a user nothing and quietly implies capabilities that do not exist. They get annotated in Phase 5, when they start carrying values.

**Keeping the unverified surface small is worth an aesthetic compromise.** `RejectionOrigin` and `RejectionReason` deserve their own titled section, which means `@UI.fieldGroup`, a qualifier and a `#FIELDGROUP_REFERENCE` facet — three more constructs that have never been activated here, in a round that already carries two. Putting them at the end of `@UI.identification` reads slightly worse and fails in exactly one fewer way. Promote them once identification and facets are proven, not before.

**Keeping the repository honest paid off as a diagnostic, not just as bookkeeping.** The Object Page stayed empty, and the obvious reading was that `@UI.facet` or `@UI.identification` had been dropped somewhere between CDS and OData. The real answer was that the root extension active in ADT was still the baseline: those annotations had never been activated at all. That took one comparison to establish, because the repository `.ddlx` holds the active state and nothing else — the annotations in `$metadata` were exactly the ones the repository showed as activated. Had the candidate source been committed as though it were live, the same symptom would have pointed at a framework bug that does not exist. A repository that tracks what is really deployed answers "is this a defect or was it never switched on?" for free; one that tracks intentions cannot answer it at all.

All of it is now verified: `#CUSTOMER`, `@UI.headerInfo`, `@UI.lineItem` on both entities, `@UI.selectionField`, `@UI.identification`, and `@UI.facet` with `#IDENTIFICATION_REFERENCE`, `#LINEITEM_REFERENCE` and `targetElement: '_Items'`.

**Two entity-level annotations, two different placement rules.** `@UI.headerInfo` activates at the top of a metadata extension, above `annotate entity`. `@UI.facet` in that same position is rejected outright — ADT returned 11 errors of the form `Annotation 'UI.facet.id' used at wrong position (wrong scope)` — and belongs inside the `annotate entity … with { }` body instead. Both annotations describe the entity rather than a single element, so assuming they shared a scope was the natural guess and it was wrong. The compiler was the only thing that could have said so. Moving the block and changing nothing else activated cleanly and rendered both Object Page facets on the first try, which is the useful shape of a placement error: once the diagnostic is read literally, the fix is mechanical and complete.

**The Phase 1 semantic annotations finished the job nobody asked them to do.** The item table renders `2 EA`, `750.00 EUR` and `1,500.00 EUR` with no unit or currency annotation anywhere in either metadata extension. `@Semantics.quantity.unitOfMeasure`, `@Semantics.unitOfMeasure`, `@Semantics.amount.currencyCode` and `@Semantics.currencyCode` were put on the base views in Phase 1 for modelling correctness, years of project-time before a UI existed, and they propagate through the projections into OData where Fiori reads them. The provisional decision to leave `UnitOfMeasure` and `Currency` out of the item columns is now evidenced rather than assumed: adding them would duplicate what the framework already renders. Annotating meaning at the lowest layer that owns it means every layer above gets it for free.

**A negative result kept its place in the record.** The invalid top-level `@UI.facet` placement stays documented alongside the working one. Deleting it once the correct form was found would have saved a paragraph and cost the next reader the same afternoon, since the wrong form is the one that looks right by analogy with `@UI.headerInfo` sitting directly above it.

## Phase 4.1 — CAP foundation, locally runtime-verified

**The evidence changes kind here, and that is worth saying out loud.** Everything from Phase 1 to Phase 3.2 rests on SAP runtime output supplied by the learner; this project's rule has been that no feature is verified without it. Phase 4 runs on a laptop, so its commands can be executed directly and their output pasted in full. That is genuinely stronger in one sense — nothing is relayed — and weaker in another, because a local Node.js process proves nothing about an SAP system. Recording it as "locally runtime-verified" rather than folding it into the same words used for the ABAP phases keeps the two claims distinguishable later, when a reader is deciding how much a status line is worth.

**A foundation that cannot start cannot be verified.** The instinct for a "foundation only" subphase is to write the manifest and stop. CAP refuses to serve an empty model, so that version of the foundation has no completion gate beyond "the files exist", which is exactly the kind of claim this project has been avoiding. One function, no entity, no persistence access, served over the adapter the later phases will use, converts the subphase from an assertion into a test. It also has to be small enough that it never becomes the thing being designed: the health service can be deleted in Phase 4.4 and nothing will notice.

**The error message pointed at the wrong layer, twice.** A correct TypeScript handler that CAP never loads reports `501 - Service "HealthService" has no handler for "ping"` — which reads as a missing handler, not as a runtime that was never told to look for `.ts` files. CAP chooses its implementation extensions from the `CDS_TYPESCRIPT` environment variable, which its own CLI sets and `node --test` does not. Separately, `cds.test(...)` failed with `Cannot find module '@cap-js/cds-test'` thrown from inside `@sap/cds`, which looks like a broken framework rather than a devDependency that moved out of the main package in version 10. Both diagnostics were accurate and both named the wrong suspect, and in both cases the fix was one line. Reading the framework source — `lib/srv/factory.js` and `lib/test/cds-test.js` are each a few lines — settled both faster than any amount of reasoning about what should have worked.

**Typechecking caught the API errors before any of them ran.** The first draft of the foundation test called `cds.shutdown()` and `cds.test.GET(...)`. Neither exists. `tsc --noEmit` rejected both with the real type shapes, which is the entire argument for ADR-008 arriving on the first file written rather than on the first bug hunted. The `Test` class turned out to extend `Axios` and expose `then`, and reading that off the type definition was quicker than reading the docs.

**Deferring `@cap-js/cds-typer` was the same restraint as Phase 3.2's annotation set.** It belongs to a TypeScript CAP project and it would have installed cleanly, and with no entities it would have generated an empty directory — a tool in the manifest that demonstrably does nothing. The `#cds-models/*` path mapping is in `tsconfig.json` because the cost of adding it now is nothing and the cost of forgetting it in Phase 4.2 is a confusing import error. Wiring a path is not the same as installing a generator with no input.

## Phase 4.2 — CAP domain model, locally runtime-verified

**The model was already written; the work was finding it.** The instinct on reaching "build the CAP entities" is to design them from the business problem, and a prompt listing plausible field names makes that feel confirmed. But `docs/architecture/domain-model.md` has carried a CAP persistence table since Phase 0 — every field, size and scale, plus the three uniqueness rules — and `API_CONTRACTS.md` carries the mapping that explains why each portal name differs from its SAP counterpart. Implementing a specification that already exists is less satisfying than designing one and is worth strictly more: the ingestion contract in 4.3 will land on fields that were defined together with it, rather than on fields invented two phases later that happen to look similar.

**The field list is where the ownership boundary is actually enforced.** ADR-004 has said "RAP owns commercial facts, CAP owns the supplier response" since Phase 0, and it is easy to agree with in prose while quietly violating it in a schema. The portal has no `CompanyCode`, `PurchasingOrganization` or `PurchasingGroup`, and no `supplierName` on the order — not because they would be hard to store, but because a portal that holds SAP's organizational context has started becoming a copy of SAP's order. `EA` becomes `PCE` at the boundary for the same reason. An architecture decision that never changes a field list is decoration.

**Association versus Composition is a lifecycle claim, and the reverse direction is the one that catches you.** `Orders.items` as a Composition and `Orders.supplier` as an Association are both obvious. `Suppliers.orders` is the interesting one: it is the same pair of entities as `Orders.supplier`, so the temptation is to mirror the relationship kind, and a Composition there would make `Suppliers` a document root whose deletion cascades into orders the portal is contractually obliged to keep. Writing a test that deletes an order and then asserts *both* that the line is gone and that the supplier survives turned the decision into something the suite defends.

**`managed` is the aspect you are supposed to add, and adding it would have been wrong.** Every CAP example applies `cuid, managed` together. `cuid` fits exactly — it contributes the UUID key the contract already specifies. `managed` would have renamed `receivedAt` to `createdAt`, which is not a cosmetic difference: in this domain the recorded fact is when the *portal received a snapshot*, not when a row was created. It would also have added `createdBy` and `modifiedBy`, two columns with nothing to populate them until Phase 4.4 has supplier identity and Phase 8 has a platform one. Phase 3.2 refused to annotate fields no code writes; the same argument applies to creating them. Keeping `@cds.on.insert: $now` — the mechanism `managed` is built from — while declining the aspect itself is the version of the convention that actually fits.

**`@assert.unique` turned out to be a database constraint, which is a stronger fact than expected.** The documented ingestion rule requires parallel duplicates to be caught "through database uniqueness and rereading the committed receipt", not by a read-before-insert check, and `@assert.unique` reads like an input-validation annotation. `cds compile db --to sql` settled it: the generated DDL contains real `CONSTRAINT … UNIQUE` clauses. Printing the DDL took one command and replaced an assumption that would otherwise have gone unexamined until 4.3 depended on it.

**One tsconfig entry cannot serve two resolvers.** cds-typer emits `index.js` for the runtime and `index.d.ts` for the compiler, and a `paths` mapping in `tsconfig.json` is honoured by `tsc` *and* by `tsx`. Every single-target choice failed, each in a different and initially misleading way: pointing at `index.ts` crashed `tsc` outright with `Error: Debug Failure`; pointing at `index.d.ts` made `tsx` execute a declaration file; regenerating as `.ts` made `tsx` load compiler input as a module and fail with `Class extends value undefined`. The fix is not a better target but a different mechanism — `moduleResolution: node16` reads the `imports` field in `package.json`, so TypeScript and Node each resolve `#cds-models/*` correctly on their own and `paths` disappears. The general shape is familiar from the Phase 3.2 `@UI.facet` placement error: three plausible variations all failed, and the resolution was to stop varying the value and question the construct.

**A boundary is worth verifying, not just declaring.** Phase 4.2 claims to add persistence and no API. Curling `/rest/supplier/v1/Orders` and `/odata/v4/Orders` and getting 404 from a server that has just deployed three tables and loaded three fixture files costs nothing and converts that claim into evidence. The startup log saying `serving HealthService` and nothing else does the same job.

## Phase 4.3 — CAP ingestion boundary, locally runtime-verified

**The framework's defaults were quietly editing the contract.** Two CAP behaviours, each sensible in isolation, each wrong here. Structured elements are flattened, so the documented nested body came back as `400 Property "source" does not exist` — the contract's shape simply was not the shape CAP intended to serve. And a `UUID`-typed key is auto-generated when the caller omits it, so a delivery with **no `deliveryId` at all** was accepted with 201 and a server-invented identity. The second one is the more alarming: it does not fail, it succeeds wrongly, converting "the body identity remains mandatory" into "optional" and destroying idempotency for that request. A test caught it because the test asserted the *refusal*, not the success. Convenience defaults are worth knowing precisely when you have an external contract to honour, because they will honour their own instead.

**Idempotency written as a check is not idempotency.** The obvious implementation is "select by deliveryId; if absent, insert". It passes every sequential test and it is wrong, because two concurrent requests can both pass the select. The contract said so already — "parallel duplicates must be resolved through database uniqueness and rereading the committed receipt" — which only became legible after writing the naive version in my head and asking what two callers would do. The constraint is the mechanism; the pre-check is an optimisation that makes the common case cheap.

**And then the branch that constraint protects was never executed.** Instrumenting the catch-and-reread path and running the concurrent test three times gave zero hits: a single local SQLite connection serializes the two requests far enough apart that the second always finds the committed receipt and takes the ordinary replay path. The invariant holds — exactly one order, one line, one receipt, both callers answered — but the code that would hold it under real write concurrency is reasoned, not exercised. Reporting "concurrency verified" would have been true of the outcome and false of the mechanism. This is the same discipline the ABAP phases needed for OI-13, arriving from the opposite direction: there the case was unreachable, here it is reachable but not reached.

**A hash is what turns "the same message" into something a computer can decide.** `{"a":1,"b":2}` and `{"b":2,"a":1}` are the same delivery; so are `1500.00` and `1500.0`. Byte comparison says no to both. The contract's instruction to "normalize known fields, decimal representation and object member ordering before hashing" is one sentence that does all the work, and the test that replays a delivery with every member reordered and every decimal rewritten is the one that proves the boundary understands business identity rather than transport accidents.

**Money is integers.** `750.0000` and `120.5000` have no exact binary representation, so `3.000 × 120.5000 === 361.50` is a coin flip in floating point. Parsing decimal strings into scaled `BigInt` makes every comparison exact and every rounding deliberate, and it costs about forty lines. The contract already said decimals travel as strings; treating that as a transport detail and converting to `Number` at the door would have thrown away the exactness the string was protecting.

**Two uniqueness rules that look like one.** `DeliveryReceipts(sourceSystem, deliveryId)` and `Orders(sourceSystem, sourceOrderId, sourceRevision)` both stop duplicates, and collapsing them would have been easy. They answer different questions: a repeated delivery is a harmless retry after a timeout, and the same order arriving under a *new* delivery id means somebody believes it was never delivered. Answering the second with a cheerful replay 200 would hide a genuine discrepancy behind a success. Keeping them separate is why the 409 can name the original portal order and the delivery that carried it, which is what a person reconciling actually needs.

**Pulling `DeliveryReceipts` forward was a documented deviation, not a silent one.** The domain model marks it phase 5. The Phase 4.3 replay and conflict rules cannot be implemented without a stored hash and a stored receipt, so it came forward — and the rest of the Phase 5 machinery, `DeliveryIntent` and `SupplierResponseDelivery` and attempt history, deliberately did not. A plan written in Phase 0 that meets an implementation in Phase 4.3 will sometimes be wrong about boundaries; the useful response is to move the boundary and say so in the schema comment, not to implement a weaker rule that fits the label.

## Phase 4.4 — CAP supplier service, locally runtime-verified

**A writable status field is a status with no rules.** The shortest path to "the supplier can accept an order" is a `PATCH` that sets `status`. It would have worked, and everything that makes the operation correct would have been optional: nothing would enforce `RECEIVED → ACCEPTED`, require a reason with a rejection, allocate the next version, or write the outbound response. Making the transition a bound action means the rule and the write cannot be separated, which is the same conclusion Phase 2.7C reached in RAP with "no unrestricted status PATCH exists". Two different frameworks, two years of project time apart, same answer — the reason is about the domain, not the technology.

**Filter the query, not the result.** Row-level isolation could be done by reading and then discarding rows the caller may not see. Adding the condition to `req.query` inside a `before READ` hook instead means the database never returns them, and — more importantly — one rule covers the collection, a key read, an `$expand` and a navigation path in one place. Every bypass I could think of to test was already closed, not because each was handled, but because there was only ever one place to handle.

**404 discloses less than 403.** For another supplier's order the instinct is 403: the row exists, the caller may not have it. But 403 *confirms it exists* and that someone else owns it, which is exactly what a probing client wants. A scoped 404 makes "not yours" and "not there" indistinguishable. The design acceptance cases anticipated this — "access denied or scoped not-found response; no fields disclosed" — and only one of those two options actually discloses nothing.

**Order the checks by what the contract promises, not by what is cheapest.** The natural order is version precondition first, since it is one comparison. The contract requires replay detection first, because "replay detection must recognize an already successful identical command even if its original version is now stale" — a retried command *must* succeed after its version has moved on. The same sentence appears again for dates: "deduplication runs before current-date validation", so a replayed command whose delivery date is now in the past is still valid. Both are cases where the cheap ordering silently breaks a retry, and retries are the normal case in an integration.

**The Phase 4.3 trap was avoided by remembering it.** Declaring `reason : String(255) not null` in the action signature reads well and made `MISSING_REJECTION_REASON` dead code: CAP's own ASSERT_MANDATORY answers first, in the framework's envelope, with no contract code and no correlation id. This is precisely what `INVALID_PAYLOAD` turned out to be one subphase earlier. Finding it took one deliberate curl of a blank reason, because the previous subphase had taught me to check reachability rather than assume it. The fix was to drop `not null` and validate in the handler, so every supplier-facing 400 speaks one envelope.

**An atomicity test has to make something actually fail.** "CAP wraps each request in a transaction" is true and proves nothing about this code. The test plants a response row occupying the `(order, version)` slot the next decision will need, so the handler's order update succeeds and its response insert then violates a real constraint from the documented model. Watching the order come back `RECEIVED` at version 0 is evidence; quoting the framework's documentation is not. The uniqueness rule that made this possible was added for a different reason entirely, which is a recurring return on modelling constraints properly.

**Pulling an entity forward twice is a pattern, not an accident.** `DeliveryReceipts` in 4.3 and `SupplierResponseDeliveries` in 4.4 are both marked phase 5 in a domain model written in Phase 0, and both are unavoidable the moment their subphase has to answer a replay. The useful response each time was to move the boundary, take only the fields the subphase needs, and say so in the schema comment — rather than implement a weaker rule that fits the original label. A plan drawn before implementation will be wrong about some boundaries; the discipline is in the record, not in the plan being right.

## Phase 4.5 — minimal supplier UI, locally runtime-verified

**Extracting the logic is what made a UI testable without a browser framework.** The instinct on reaching "test the frontend" is to reach for Playwright. Almost nothing here needed a browser: which controls a status permits, what a command payload contains, how an error becomes a sentence — all of it is a pure function of data. Putting those in `app/lib/order-view.mjs` with no DOM and no fetch, and importing *that same file* in the tests, covered the parts that can be wrong. What was left needing a real browser was rendering, and rendering is exactly what a test would have asserted badly anyway.

**And then the browser found the one bug the tests could not.** The first render showed the sign-in panel and the signed-in bar simultaneously, because `#session { display: flex }` is an author rule and beats the user agent's `[hidden] { display: none }`. Every panel toggled by `hidden` was permanently visible. No unit test would have caught it, no HTTP test could have, and it took about four seconds of looking at a screenshot. The lesson is not "write browser tests" — it is that a class of defect exists only in the rendered result, and the cheap way to find it is to look.

**A UI that mirrors backend rules has to mirror them and nothing more.** `actionsFor(status)` decides which buttons to draw and is, unavoidably, a copy of the lifecycle. The discipline is in what it is *allowed to be*: it decides visibility, never permission. A wrongly drawn Accept button on a rejected order produces a 409 from the service, not a wrong write. Stating that boundary explicitly is what keeps a convenience mirror from quietly becoming a second rulebook — the same reason the reject box checks for a blank reason and the service still enforces it.

**Idempotency has a frontend half.** The backend's `responseId` replay detection is worthless if the browser generates a fresh id on every retry. Minting one id per *user command* rather than per HTTP attempt is the part that makes a double-click harmless, and it is invisible in the backend code. The same is true of `expectedResponseVersion`: taking it from the loaded order, never from an input field, is what makes it an observation rather than a wish.

**Refusing to retry is a feature.** The obvious response to 409 `STALE_RESPONSE_VERSION` is to reload and resend. That would be wrong: the order changed, so the decision made a moment ago may not be the one the supplier would make now. Reload, show what happened, stop. There is no retry logic anywhere in this UI, and that absence is deliberate.

**Deciding not to add a field was the pagination design.** The contract asked for "query parameters and result envelope". Parameters were easy. The envelope was the real choice: wrapping the array in `{ items, count }` is conventional, and it would have changed a read contract Phase 4.4 had already verified and tested, in exchange for a count nothing in this portal displays. Keeping the bare array and paging until a short page arrives costs one helper function and keeps the count available as a later additive change. Not paging the item list at all was the same kind of decision from the opposite direction — a bound where ingestion already guarantees one would only risk truncating a detail view.

## Phase 4.6 — Phase 4 closure, consolidated verification

**Five subphases each verified in isolation are not the same as a verified system.** Every Phase 4 subphase ended green, and the closure pass still found five real inconsistencies. None was a code defect — the code was exercised each time and stayed right — and all five were prose about the code that had quietly gone stale: a guide describing a service as not existing after it had been built, a limitation recorded as open after it was resolved, an error-code count that a later subphase had invalidated. That asymmetry is the lesson. Tests defend behaviour continuously; documentation has nothing defending it except a deliberate pass, so the pass has to be scheduled rather than hoped for.

**The test reporter had been lying to me since Phase 4.3, gently.** Node prints top-level entries, and a standalone `test()` outside any `describe()` is printed among them. `health.test.ts` has exactly one, so the printed numbering has run one ahead of the suite count for four subphases, and three guides inherited the confusion by calling an entry range "suites". The arithmetic mistake was trivial; the interesting part is that a per-phase count of 8, then 14, then 20 suites looks perfectly self-consistent while the entry ranges quoted beside them are all off by one. A number can be internally consistent and still describe the wrong thing.

**Superseded evidence should be reframed, not deleted.** The Phase 4.3 guide records `GET /rest/supplier/v1/Orders -> 404` as proof that Phase 4.4 did not exist yet. That statement is now false and the evidence is still valuable: it shows the boundary was verified rather than assumed at the time. Deleting it would erase the proof; leaving it unqualified would be a lie. Framing it as a checkpoint keeps both. This is the same instinct as the Phase 3.2 `@UI.facet` negative result — a record of what was true then is worth as much as a record of what is true now, provided the reader can tell which is which.

**Closing a phase is also deciding what it is not allowed to claim.** The honest summary of Phase 4's concurrency story is uncomfortable: idempotency, identity reuse, stale versions and atomicity are all verified, and **no concurrent race was ever exercised on either service**. The constraints that would hold those invariants under real concurrency are proven to fire — the atomicity test works by triggering one — but the concurrent code paths are reasoned. Writing that down as a limitation rather than letting "idempotency verified" stand unqualified is what makes the rest of the claims worth anything.

**A handoff is a list of identifiers, not a plan.** The temptation at the end of a phase is to start designing the next one. What Phase 5 actually needs from Phase 4 is seven names — `deliveryId`, `sourceSystem`, `sourceOrderId`, `sourceRevision`, `portalOrderId`, `responseId`, `responseVersion` — each with an owner and a role, plus the fact that there are no cross-database foreign keys anywhere. That list was fixed in the Phase 0 domain model, survived five subphases of implementation unchanged, and is the entire contract. Everything else Phase 5 will decide for itself.

## Phase 5.1 — SAP → CAP outbound foundation, design only, not runtime-verified

**Nothing here was executed.** No ABAP object was created, no HTTP request was made and no compiler ran. These are findings from reading the two systems' sources against each other, which is a weaker kind of evidence than every lesson above it and is labelled as such.

**Reading the other system's validator is how you find the gap the plan hid.** `OrderRevision` looked finished: the column exists, the CDS view exposes it, the BDEF maps it and marks it `readonly`, and the domain model says it starts at 1. It holds `0` on every row, because "no handler writes it" is a fact you get only from grepping the behavior pool for `UPDATE FIELDS` — there are eight, and none of them touch it. That alone is just recorded debt. It becomes a blocker two systems away, in a TypeScript file, where `normalizeDelivery` refuses `source.revision < 1` with `INVALID_SOURCE_IDENTITY`. Neither side is wrong on its own terms and the contract between them is satisfied on paper. An integration's first real failure tends to live in exactly this shape of gap, and the cheap way to find it before dispatch day is to read the receiver's validation rather than the sender's field list.

**The tempting fix was the wrong one, and it was tempting for a bad reason.** Mapping `0` to `1` inside the outbound builder is one line, needs no activation round, and breaks nothing visible. It also relocates a business fact into a transport component: `sourceRevision` participates in CAP's `Orders(sourceSystem, sourceOrderId, sourceRevision)` uniqueness, so the revision is what decides whether a re-sent order is a duplicate or a new version of itself. A mapper inventing that is a mapper deciding deduplication. Writing it in `submit`, where the revision actually becomes frozen, costs a subphase and an updated EML test, and keeps the fact where it belongs — the same argument ADR-023 made about drawing the purchase order number at submission rather than earlier.

**An identifier with an assigned owner and no column is a plan, not a design.** The Phase 4.6 handoff lists `portalOrderId` with the role "what SAP stores to refer to the portal's copy". Six of the seven identifiers had a home; that one had none, in `ZJP_PO_H` or in the domain model's field list. It survived being written down, reviewed and carried across a phase boundary because a table of names with owners reads like completeness. The useful question on any handoff list is not "is the name right" but "which column is it going to sit in", and asking it also answered *where*: the receipt belongs to one delivery, not to an order that may be delivered again at a later revision, so a header column would be overwritten while a row per intent keeps each receipt beside the payload that earned it.

**An exception is the wrong return type when ambiguity is the interesting case.** The idiomatic ABAP transport raises on failure. That single failure channel destroys the distinction the whole outbox exists to preserve — API_CONTRACTS says "a timeout never proves non-delivery", and "definitely not delivered" and "possibly delivered" demand opposite actions: one retries, the other replays the *same* `deliveryId` and reconciles. Collapsing them is precisely how a system creates a second order for a delivery CAP already committed, which is the failure `DeliveryReceipts` was pulled forward in Phase 4.3 to survive. So `post` returns a record whose `answered` flag is a first-class value. The classification is then deliberately conservative: everything unanswered becomes `UNKNOWN`, even a connection refused that probably does prove non-delivery, because being wrong in that direction costs one replay that Phase 4.3 verified is safe, and being wrong in the other direction costs a duplicate order.

**Which artifact to freeze was decided by the phase after next.** The immutable snapshot could hold either DTO in API_CONTRACTS. Freezing the mapped CAP order is the obvious choice — it is what actually gets posted — and it would have invalidated every intent written in Phase 5 the moment Phase 6 moved the endpoint to Cloud Integration, which expects the *source* delivery and does its own mapping. Storing the source snapshot and re-deriving the mapped body per attempt is only affordable because of something Phase 4.3 verified rather than assumed: CAP's replay hash is taken over a normalized projection with explicit separators, not over raw bytes, so a deterministic mapper gives semantic stability without byte stability. A verified detail of the receiver's implementation decided a persistence choice in the sender.

**"The repository has no reference to this API" is a result worth writing down.** Searching for `if_web_http`, `cl_web_http`, `cl_http_destination` and `IF_HTTP` across every ABAP and Markdown file returns nothing. That is not an absence of information, it is the finding: four phases of this project have been built without ever touching outbound communication, so the single most load-bearing assumption in Phase 5 has no support anywhere in the repository. The honest output is a probe list — twelve of them — rather than plausible ABAP written from memory that compiles in a reader's head and not in ADT. The Phase 3.2 `@UI.facet` result is in this file because a negative compiler answer was recorded; a probe is the same instinct applied before the code exists instead of after.

**A lesson does not transfer just because the rule is the same.** Phase 4.3 concluded that idempotency belongs in a database constraint rather than a read-before-insert check, because two concurrent requests can both pass a check. The same rule — one delivery per order revision — arrives on the RAP side, and the conclusion does not simply carry over: whether a `DEFINE TABLE` artifact under ABAP Cloud can even carry a unique secondary index is not something this repository knows. RAP's root lock is a genuinely stronger starting position than two unserialized HTTP POSTs, and it is also reasoning rather than evidence, on a system where OI-13 records that no concurrency case has ever been run. Carrying a lesson across a technology boundary means re-earning it there.

## CAP HANA production preparation — configured and locally verified, not deployed

**Nothing ran against HANA.** These lessons come from configuration, generated DDL and local execution. No schema was deployed, no query was issued on HANA and no binding exists, so nothing below is evidence about HANA's runtime behaviour.

**`cds add hana` reported success and left production on SQLite.** The command did exactly one thing — added `@cap-js/hana` to `dependencies` — and printed "Successfully added features to your project". Production still resolved to SQLite `:memory:`, because the Phase 4.1 `.cdsrc.json` pinned `requires.db` with no profile qualifier, and an unqualified `requires.db` applies to every profile. A generator that only adds is powerless against configuration that already asserts the opposite, and it has no reason to warn: from its point of view the dependency is now present and its job is done. The lesson is to verify the *effect* rather than the exit code — `cds env requires.db --profile production` took one second and contradicted the success message.

**The dangerous state was the intermediate one, and it was silent.** With the dependency declared but the SQLite pin still in place, `cds build --production` began emitting HDI tables and indexes while the runtime configuration would still have opened an in-memory SQLite. That combination deploys a database schema and then ignores it. Neither half looks wrong on its own: the build output is correct HANA, the runtime config is valid CAP. Only comparing the two reveals it, which is a good argument for treating "what does the build emit" and "what will the runtime connect to" as two separate questions that each need their own check.

**The fix was a deletion, and that was the design decision.** The instinct was to add `requires.db.[production].kind = "hana"` beside the existing SQLite block. Reading the two plugins' own `package.json` files showed why that would be wrong: `@cap-js/sqlite` declares `requires.db = "sql"` with `kinds.sql.[development]`, and `@cap-js/hana` declares `kinds.sql.[production]`. The composition already exists and is maintained by the people who wrote the adapters. Restating it in the project file would duplicate it, drift from it on the next upgrade, and re-create the same failure one profile further along — the `[hybrid]` profile, which neither the project nor I had thought about, is handled correctly for free by exactly the same mechanism. Removing the project's opinion made the configuration shorter *and* more correct, which is rare enough to notice. The authoritative source for how to configure a plugin is the plugin, not a remembered snippet.

**A build command nobody has run is an untested code path.** `cds build --production` failed with `TS2210` — and it failed identically on the clean baseline, with no HANA involved. Four completed CAP subphases had verified installs, typechecks, tests, DDL compiles and a running server, and none of them had ever produced a deployable build. The gap was invisible because every *other* gate was green and each one felt like it covered the toolchain. Verification is only as wide as the commands actually executed, and "the project builds" was an assumption, not a result.

**Reading the plugin's source beat reading its error message.** `TS2210` talks about an ambiguous project root and an import map entry, which suggests a `tsconfig.json` problem. The actual cause was a filename: `cds-typer`'s build plugin looks for `tsconfig.cdsbuild.json` and, finding none, falls back to `tsc --outDir gen/srv` — and the plugin's own source comment describes the file it wants, including which folders to exclude. Thirty seconds in `node_modules` produced the supported answer; guessing at `rootDir` in the shared `tsconfig.json` would have produced a plausible fix that also perturbed the typecheck, which Phase 4.2 had already fought hard to stabilise.

**A guarantee about a service surface is not a guarantee about the persistence layer.** Phase 4.3 established that `IntegrationService.Orders` "exposes no persistence", and the HANA build emitted `IntegrationService.Orders.hdbtable`. Both are true. The claim was always about routes — `@insertonly`, `GET` returns 405, no generic CRUD path — and the compiler gives any entity definition with its own elements a table regardless of who can reach it. In SQLite `:memory:` the extra table was invisible; a HANA build makes it a deployable object. Compiling for a second database did not change the model, it changed what could be *seen* about the model, and the Phase 4.6 count of "5 tables" turned out to be scoped to `cds compile db --to sql` and the `db/` folder rather than to the whole application. *Resolved later as OI-14 item 1: `@cds.persistence.skip` now closes the gap between the two claims, so the service-surface guarantee and the persistence reality finally agree.*

**Preparing to deploy is what surfaces everything deployment would expose.** The build output contains the three mock users and the CSV fixtures. Neither is a defect — authentication is Phase 8 and the fixtures are the documented test data — and both would have gone to a cloud endpoint the moment someone pushed. A deployment artifact is a much more honest inventory of a project's unfinished business than its source tree is, because it contains precisely what would become real. *The fixtures half was resolved later as OI-14 item 3, by moving them into CAP's development-only `test/data` folder; the mock users remain.*

## OI-14 item 1 — removing the ingestion contract's phantom table, build-verified only

**Nothing here touches HANA at runtime.** The evidence is a compiler source reading, a byte comparison of generated metadata, and a local test run. No schema was deployed and no query ran on HANA.

**`@insertonly` answers "who may call this", not "is this stored".** That conflation is what produced the phantom table in the first place. Phase 4.3 wrote `@insertonly` on the ingestion contract entity and read the result as "this exposes no persistence", which was true of every route and silently false of the database. The two questions have separate annotations and separate compiler phases, and only `@cds.persistence.skip` answers the second. A guarantee is only as broad as the mechanism enforcing it, and the mechanism here was an OData restriction being asked to do a persistence job.

**The argument for the annotation came from the entity's semantics, not from the artifact being untidy.** "Delete the empty table" is a cleanup; the actual justification is stronger and worth stating as the reason: this entity is never read, queried, navigated to or written, and its key carries the caller's `deliveryId` for idempotency rather than identifying a row. The table was not unused, it was *unusable* — and deploying it would have published an object implying exactly the persistence path ADR-028 was designed to deny. The artifact contradicted the architecture that generated it, which is a better reason to remove it than the file count.

**Reading the compiler settled in minutes what documentation would have left ambiguous.** The open question was whether the annotation would also strip the entity from the service. `lib/transform/db/cdsPersistence.js` sets `$ignore` on the artifact and lives in the database transform; grepping the OData/EDM transform for the annotation returns nothing. That is a sharper answer than any prose, and it also surfaced the single failure mode worth checking — a view or join-relevant association navigating *into* a skipped entity raises `ref-invalid-assoc-navigation` — which then took one query of the compiled model to rule out. Verifying an annotation against the tool that implements it costs less than one debugging session on a bad guess.

**Byte-identical generated metadata is the assertion worth making about a contract change.** "The tests pass" would have been true of several wrong versions of this change. Compiling the service to EDMX before and after and diffing it proves the thing actually promised — that the wire contract did not move — and it caught nothing, which is the point: the claim is now backed rather than hoped.

**A comment is not automatically inert.** The explanation was first written as `/** */` directly above the entity, and the compiler warned that it overwrote the entity's existing doc comment. A doc comment is model metadata, so documenting the change would have quietly altered the description the change was supposed to leave alone. The lesson is small and general: in a language where comments can be syntax, check which kind you are writing.

## OI-14 item 3 — fixtures out of the production build, by folder rather than by flag

**Build-output evidence only.** Nothing was deployed or bound, so none of this says anything about HANA at runtime.

**The framework had already made the distinction; the project just was not standing in it.** The instinct on "keep test data out of production" is to reach for configuration — an exclude list, a skip flag, a profile override on `requires.db.data`. None was needed. `@sap/cds/lib/env/cds-requires.js` declares seed folders per profile, giving `[development]` the folders `db/data`, `db/csv` and `test/data` while `[production]` gets only the first two. So `test/data` already *is* the development-only seed folder, and the entire fix was moving three files into it. Reading the defaults before writing configuration turned a config change into a `git mv`.

**The defect was the folder, not the data.** It is tempting to describe this as "test fixtures were leaking into production", which frames it as an accident. It was structural: `db/data` is read under both profiles, so anything placed there is deployed *by construction*, and the fixtures were behaving exactly as their location specified. That reframing matters because it picks the fix. A flag would have left the trap in place for the next CSV someone adds; moving the folder makes the exclusion a property of where files live, and a fixture can no longer leak by being forgotten.

**This is the second time the corrective change was a deletion or a move rather than an addition.** ADR-033 fixed the production database by *removing* a `requires.db` pin that fought CAP's own profile composition. ADR-035 fixed production seed data by *moving* files into the folder CAP already scopes by profile. Both times the first draft of the fix was "add configuration to express what I want", and both times CAP already expressed it and the project's own settings were the thing in the way. The pattern worth remembering: when a framework seems to need configuring to do something obvious, check whether it already does it and something local is overriding it.

**"Local development still works" needed two different proofs, because the tests only cover one path.** The suite passing proves seeding works under `cds.test`. It does not prove `npm start` works, which is the actual developer workflow, and the two could in principle resolve profiles differently. Starting the real server and reading its log — `init from test\data\pih.portal-Suppliers.csv`, then a live query returning the same three orders to the same two suppliers — cost about a minute and closed a gap the green suite would have hidden. A test suite is evidence about the test harness first and the application second.

**A path in a comment is still a path.** One test file carried `/** Fixture ids from db/data … */`, which became false the moment the files moved. Correcting a comment is not editing a test expectation, and the distinction is worth keeping clear: the assertions were untouched, and the only thing changed was a sentence that would otherwise have sent the next reader to a folder that no longer exists.

## OI-14 item 2 — XSUAA production security prepared, and one question only the cloud could answer

**Token-level cloud evidence plus local execution.** CAP is not deployed, so nothing here proves a deployed application enforces the scope, and no secret, service key or token is recorded anywhere in this repository.

**`authenticated-user` was the wrong tool, and the reason generalises.** It reads like "require a login", and for a portal that is nearly right. It is wrong here for two independent reasons. CAP's `cds compile --to xsuaa` treats it as a hardcoded pseudo-role and emits **no scope at all**, so nothing reaches `xs-security.json` — the security model would have compiled to an empty descriptor. And a client-credentials token *is* an authenticated user, so SAP's technical client would have satisfied the supplier service's requirement and could have read supplier orders. A pseudo-role cannot express "which kind of caller"; only a named role can, which is precisely what ADR-005 separated the two services to preserve.

**A scope and a role-template do not give the application's own client that scope.** This was the assumption worth paying to test. Everything looked complete: two scopes, three role-templates, a generated descriptor, CAP requiring the right role. A `client_credentials` token from a real XSUAA instance carried exactly one scope, `uaa.resource`. Role-templates are the path for *interactive* users, consumed through role-collections assigned to people; they contribute nothing to a technical client. Top-level `authorities` is the mechanism for the app's own client. Two adjacent keys in the same file, doing unrelated jobs, and no amount of reading the model would have revealed which one was load-bearing — a ten-minute probe did.

**The probe was worth more than the fix.** The change itself is three lines of JSON. What the probe bought is knowing that the model as designed would have failed at SAP's very first call, and failed in the most expensive way: after deployment, in someone else's system, with a 403 and no obvious cause. Spending a free Trial service instance to convert a reasoned claim into an observed one is the cheapest security testing available, and the finding was negative — which is exactly the kind that never shows up in a review of the source.

**Grant the technical scope, and only the technical scope.** `authorities` lists `IntegrationClient` and deliberately omits `SupplierPortalUser`. The temptation is to list both "for completeness", which would silently hand every machine token the supplier surface and undo the separation the named roles were introduced to create. The probe confirms the supplier scope is absent from a technical token, so the isolation is observed rather than intended. `grant-as-authority-to-apps` was left alone for the symmetric reason: it targets a *foreign* XSUAA application, and inventing one to model SAP would have described an architecture that does not exist.

**A declarative rule that changes an error code is not a refactor.** `@restrict ... where: 'supplierCode = $user.supplier'` is the idiomatic CAP way to express row-level authorization, and it does make the compiler emit the `supplier` attribute — so it was tempting twice over. With `grant: 'READ'` the bound actions lost permission; with `grant: '*'` a foreign supplier's order answered **403 where the contract documents a scoped 404**, and 404 was chosen deliberately because a 403 confirms the row exists and belongs to someone else. A change that swaps one of those for the other is a disclosure change wearing the costume of a cleanup. Enforcement stayed in the handler and the attribute moved into the descriptor by hand.

**Not hardcoding an identity is a decision, and it has a visible cost.** `xsappname` is absent from the tracked descriptor so the deployment descriptor owns the application identity — and `cf create-service` refuses a descriptor without one, which is how the absence was discovered rather than assumed. The probe used a scratchpad copy carrying a throwaway name, keeping the probe's identity out of the repository entirely. Sometimes the right artifact is deliberately incomplete, and the honest response is to record what supplies the missing piece rather than to fill it in locally.

**Measure twice when the measurement is the evidence.** Checking for stray carriage returns, one `grep -c $'\r'` reported zero and a later one reported forty-four on the same unchanged file. The second was wrong: nested inside a command substitution the `$'\r'` degraded to a literal `r`, so it had been counting lines containing that letter. A byte-level read settled it at zero. The lesson is not about quoting — it is that a verification step can fail silently and report a plausible number, so a claim about bytes deserves a tool that reads bytes.

## First Cloud Foundry deployment — auth enforcement verified, HANA still untouched

**Real cloud evidence for deployment, startup and authorization; none for HANA data.** The application runs and answers, but no business row has been written to or read from the database, so nothing here says anything about HANA's storage or SQL behaviour.

**A `start` script is a deployment artifact, not a developer convenience.** `"start": "cds-tsx serve"` was correct for four subphases of local TypeScript work and was the single line that broke the first deployment. `cds build --production` copies the root `scripts` verbatim into `gen/srv/package.json`, so the container's entry point *is* the development command, and `cds-tsx` lives in `@sap/cds-dk` — a devDependency that a production install omits. Staging succeeded, the buildpack was fine, Node was fine, and the process died in one line with exit 127. The generalisable part: anything in the root manifest that the build copies into the deployed module stops being local-only the moment there is a deployment, and `start` is the least obvious member of that set because it looks like tooling rather than configuration.

**The error named the symptom two layers from the cause.** `sh: 1: cds-tsx: not found` invites the fix "make `cds-tsx` available", which would have meant promoting the whole development toolkit into production dependencies to ship a TypeScript transpiler that the runtime does not need. The actual question was *why a TypeScript runner was being invoked at all*, and the answer was that it should not be: `cds build --production` had already compiled every handler, and `gen/srv` contains zero `.ts` files. The cheapest fix and the correct fix pointed in opposite directions, and the correct one was smaller.

**Precompilation is what makes the production runtime boring.** Because the build emits plain JavaScript, the deployed container needs `@sap/cds` and nothing else from the TypeScript world — no `tsx`, no `typescript`, no `cds-dk`. That is worth stating as a design property rather than a coincidence: the TypeScript decision from ADR-008 costs nothing at runtime precisely because it is resolved at build time. The price is paid in the development workflow instead, where `npm run watch` now carries the TypeScript story and `npm start` means production.

**Authorization designed in configuration is not authorization until something enforces it.** Three prior steps established named roles, a generated `xs-security.json`, and a token-level proof that `authorities` puts the scope in a technical token. None of them proved that a deployed CAP would *check* it. The live probe closed that in four requests: 401 anonymous, 200 authenticated on health, 400 from our own handler on ingestion, 403 on the supplier surface. The 400 is the one that mattered — a business validation error is the proof of entry, because a framework rejection would have been 401 or 403 and never reached the code that produced a correlation id.

**"Reuse the existing service" is only proven by a deployment that does not duplicate it.** The `org.cloudfoundry.existing-service` resource was schema-valid and documented, and the real test was counting instances afterwards: one HANA Cloud database, one HDI container, bound to both the application and the schema deployer. Before the deploy that claim rested on a descriptor and a reading of SAP's examples; after it, on the space itself.

**A stale local server produced a convincing false positive.** Testing whether `gen/srv` could start under the production command, the health endpoint answered 200 — from a server left running hours earlier on the same port, which the log revealed with `EADDRINUSE` and a three-hour uptime. The reported uptime is what gave it away. Any local verification that binds a well-known port should either check what is already listening or use a port nothing else could hold, because a passing result from the wrong process looks exactly like success.

## First HANA runtime verification — the ingestion path, exercised at last

**Real cloud evidence, and deliberately partial.** One valid order was ingested through the deployed application with a real XSUAA token and verified in the `pih-hdi` container. Every write exercised was an INSERT, so nothing here says anything about UPDATE behaviour on HANA. No secret, token or service-key content is recorded in this repository.

**An empty table is evidence, and it was the first thing worth reading.** The container held zero rows in all four tables while all four existed and were queryable. Two separate claims fell out of one query: the HDI deployment worked, and ADR-035's profile-scoped fixture folder actually kept synthetic data out of production. The fixture exclusion had been argued from CAP's seed-folder defaults and then from the build output — three `.hdbtabledata` files becoming none — and both are inferences about what *would* happen. Counting rows in the real container is the first evidence about what *did*. Absence is awkward to prove and cheap to check, and checking it converted two build-time arguments into runtime facts for the price of one `SELECT`.

**The 201 was the weakest evidence in the whole exercise.** A create returning 201 with a plausible receipt proves the handler ran and chose to answer; it does not prove a row exists, that the commit landed, or that the values survived. The receipt could have been assembled entirely from the request. What made the result trustworthy was querying HANA afterwards and finding the `portalOrderId` from the response body attached to a row whose decimals still read `37.50`, `3.000` and `12.5000`. The general habit: when a system reports its own success, verify through a different door than the one it answered.

**Computing the expected hash before sending turned a stored value into a checked one.** The `requestHash` in the receipt row could have been anything; finding *some* hash there would have looked like success. Running the payload through the application's own `deliveryHash` locally first produced the exact string to expect, and the stored value matched it. That is the difference between "the dedup key is present" and "the dedup key is right", and it cost one line. The same move made the replay test sharper: the byte-different variant was hashed locally and confirmed equal *before* it was sent, so a 200 was a prediction confirmed rather than a result interpreted.

**`modifiedAt` was the assertion that made "nothing changed" mean something.** The obvious check after a replay and a conflict is that row counts are unchanged, and they were. But counts cannot distinguish "no write happened" from "the row was overwritten in place" — and `modifiedAt` carries `@cds.on.update: $now`, so any UPDATE would have moved it. Comparing the full row byte for byte, timestamp included, is what turns "no duplicate was created" into "no write occurred at all". Choosing an assertion that a wrong implementation would fail is the whole job; a count would have passed for an implementation that silently overwrote the order.

**A byte-different replay is the test the contract actually specifies.** Resending identical bytes proves a cache-like lookup works. The contract says something stronger — that normalization happens before hashing, because *"raw JSON byte order alone is not a meaningful equality check"* — and only a message that differs in bytes while matching in business content can test it. Reordering the keys and writing `37.5` for `37.50` cost nothing and exercised the clause that a naive implementation would fail while passing the identical-bytes test.

**Verifying the mechanism before using it kept the test honest.** The task needed to read and seed a deployed database, and the supported route — a CAP-aware Cloud Foundry task over the application's existing binding — was verified with a read-only probe first: it printed the resolved profile, the database kind and the service class before anything was written. That probe is what established `production` / `hana` / `HANAService`, which is the single most load-bearing fact in the whole verification, because without it every later query might have been hitting something other than HANA. Running the cheap read-only version of a mechanism first is not caution, it is how the expensive version becomes interpretable.

**The remaining gap is a shape, not a quantity.** It is tempting to read "one order ingested" as partial progress toward HANA confidence, as though more orders would finish it. They would not. Every write exercised was an INSERT, so what is unverified is a *kind* of operation: the supplier decision path's UPDATE, the `responseVersion` increment, the `@cds.on.update` trigger firing, and `SupplierResponseDeliveries` receiving its first row. Splitting the open item by path rather than reporting it as a percentage is what keeps the next step obvious.

## First SAP → CAP outbound runtime probe — the pipe, proven end to end

**Real SAP runtime evidence, supplied by the learner, and deliberately narrow.** An outbound call from the S/4 sandbox reached the deployed CAP application and completed a full ingestion, replay and conflict sequence. The payload was hand-built, so none of the business outbound flow is evidenced: no RAP order was mapped, `sendToSupplier` does not exist, and no ABAP object from the Phase 5.2 inventory was created. No client secret or access token is recorded in this repository.

**The 401 was the result worth celebrating.** Before OAuth was configured, the destination connection test returned HTTP 401, which looks like a failure and was the single most informative outcome in the sequence. Only the CAP application can produce that 401 — a DNS failure, a routing problem, an untrusted certificate or a stopped app all fail earlier and differently. So one refusal simultaneously proved name resolution, network path, TLS trust and a running application, and narrowed everything remaining to credentials. The general habit: when diagnosing a chain, the most valuable error is the one that could only have come from the far end.

**The candidate API set was wrong, and recording it as a candidate is what made that cheap.** Phase 5.1 named `cl_http_destination_provider` with `create_by_url`, `create_by_comm_arrangement` and `create_by_cloud_destination`, and refused to write an implementation against them. The chain that actually worked was `CL_OUTBOUND_PROVIDER_HTTP=>CREATE_BY_DESTINATION` into `CL_WEB_HTTP_CLIENT_MANAGER=>CREATE_BY_HTTP_DESTINATION` — a different class, reached by destination name. Had the repository authored plausible ABAP from memory, the error would have surfaced as a compile failure inside a half-written transport class, entangled with design decisions, instead of as a probe answering cleanly. The discipline cost one paragraph and saved a debugging session.

**A certificate lesson is a fact about one chain, not a rule.** The first handshake failed with `SSSLERR_PEER_CERT_UNTRUSTED`, and importing DigiCert TLS RSA4096 Root G5 into the ANONYM PSE fixed it. The temptation is to write that down as "Cloud Foundry needs DigiCert G5", which would be wrong in a useful-sounding way: it is the anchor this route's chain happened to need at this moment, and chains rotate. Recording the specific root alongside the specific PSE and the specific error keeps the note actionable without turning one observation into a policy that will quietly expire.

**Idempotency proven from the developer machine is not the same evidence as idempotency proven from SAP.** The replay and conflict behaviour had already been verified against the deployed app, and repeating it from ABAP could have looked redundant. It was not: the SAP path serializes the payload through a different JSON writer, a different HTTP client and a different TLS stack, any of which could have altered bytes in ways that change a hash. The identical `portalOrderId` and the *original* `receivedAt` coming back to ABAP is what proves the normalization survives the real sender, which is the only sender that will ever matter.

**Proving the pipe is not starting the flow, and the wording has to hold that line.** It is tempting to read a 201 from ABAP as "`sendToSupplier` works". What was sent was a hand-built payload with fixed UUIDs and a revision chosen to satisfy CAP. The real flow still has to read a RAP purchase order, populate `OrderRevision` — which is `0` on every row and would be rejected outright — mint and persist a `DeliveryId`, drive the `IntegrationStatus` lifecycle, and write the HTTP outcome back inside a defined transaction boundary. The probe removed the transport risk and none of the business risk, and the remaining open probes (P5–P11) reflect that exactly: every one of them is about constructing a payload rather than sending it.

## Phase 5.2a — two header values, and why the guard was the risky part

**SAP runtime-verified.** The learner activated `ZBP_I_PURCHASEORDER` and `ZJP_CL_PO_EML_TEST` and ran the full EML suite through its final summary with no `STOP`. Two existing classes changed and no object was created.

**The dangerous edit in this slice was the guard nobody asked about.** `initializeStatus` filters its work with `DELETE purchase_orders WHERE Status IS NOT INITIAL`, and the obvious-looking move when adding a second initial value is to widen that guard to cover the new field too. It would have been a data-corrupting bug: every row persisted before this phase has a filled `Status` and a blank `IntegrationStatus`, so a guard keyed on the blank integration value would have classified live orders as uninitialized and reset their `Status` to `DRAFT`. The guard had to stay exactly as narrow as it was. The lesson is that when a determination gains a field, its *filter* is the part to leave alone, because the filter encodes what "new" means and the new field does not share that meaning for historical rows.

**Asserting in the buffer proved authorship in a way the committed row could not.** After a commit, `OrderRevision = 1` only shows that *something* wrote it. Reading it out of the RAP buffer between the `EXECUTE submit` and the save shows it was the action, not a determination, a save handler or a side effect of the number allocation. Where a value comes from matters here because the whole point of B1 was rejecting the alternative of defaulting `0` to `1` further downstream, and an assertion that cannot distinguish the two would not have defended the decision it exists to defend.

**The negative case carried the requirement, and it came free from existing structure.** "A failed submit must not assign revision 1" sounds like it needs a new guard. It needed none: `submit` already wraps its work in `DO 1 TIMES` with `EXIT` on every refusal, so every validation, the draft rejection and the number-range failure all leave the method before the update statement. Adding a field to that statement inherited all of it. Reading the control flow before adding code turned a requirement into an assertion rather than a feature.

**Extending one determination beat adding a second.** Both `Status` and `IntegrationStatus` answer the same question — what a newly created root starts as — and two determinations on the same `on modify { create; }` trigger would have duplicated the read, written twice, and carried no ordering guarantee between them. Putting both in one `UPDATE FIELDS` also makes a half-initialized root impossible rather than merely unlikely, which is the kind of guarantee worth preferring over a check.

**An explicit initial value is worth more than a convention about blank.** B2 offered two defensible options: treat blank as `NOT_REQUESTED` when reading, or write `NOT_REQUESTED` on create. The second was chosen because the first spreads a special case into every future reader, and the first reader to forget it would be a bug with no obvious home. Writing the value once moves the decision to the place that owns initialization.

**The lifecycle summary revealed a semantic the tests were not asserting.** Printing the revision beside the status showed that orders which passed through submit carry `1` even after becoming `APPROVED`, `REJECTED` or `CANCELLED`, while an order cancelled while still pre-submit retains `0`. That is the frozen-at-submission rule behaving correctly, and it says the revision tracks *"was this ever submitted"* rather than the current business status. Diagnostic output that prints adjacent facts together earns its keep by making a property visible before anyone thinks to assert it.

**A comment can be falsified by a change that leaves its conclusion intact.** Two places justified the missing ADR-022 delivery guard with "nothing can set IntegrationStatus or DeliveryId". After this slice something can — but only to `NOT_REQUESTED`, which is precisely the state meaning no delivery was requested, so the guard is still unrepresentable and still untestable. The conclusion survived and the reason did not, which is the easiest kind of documentation rot to miss: nothing breaks, and the next reader inherits a false premise supporting a true claim.

## Phase 5.2b — activation findings, and what the database does when you break it

**Phase 5.2b is SAP runtime-verified.** The revised `ZJP_CL_PO_EML_TEST` suite completed with `PASS: Phase 5.2b DeliveryIntent persistence verified.` and reached `=== END LIFECYCLE SUMMARY ===` with no `STOP` and no short dump. Mixed evidence underneath, and the distinction still matters: three of the lessons below are ADT **compiler** results, three are **runtime** evidence about the physical unique index — including an ST22 dump — and the uniqueness constraint is verified **manually** rather than by the automated suite, for the reason the last lesson gives.

**A Table Index can be active in DDIC and not exist in the database, and the test told the truth about that before anyone noticed.** The Table Index object `ZJP_PO_DLV~REV` was created and activated, and the duplicate-revision test then **persisted two rows**. Nothing was wrong with the index definition; the physical database index simply had not been created yet, and activation of the DDIC object did not by itself create it. **SE14** was needed to confirm and create the database-level index, after which SE11 shows `REV` as unique and SE14 shows the index present. The lesson generalises past indexes: an active dictionary object is a statement about the dictionary, not about the database, and a constraint you have not seen refuse anything is a constraint you have not verified. Had the test asserted "the index works" from the DDIC object's activation status, it would have reported success while two rows sat in the table.

**A physical unique-index violation during a managed RAP save dumps; it does not come back as FAILED.** With the index physically present, a second intent for the same `(CLIENT, PURCHASE_ORDER_UUID, ORDER_REVISION)` — carrying a *different* generated `DeliveryUUID` — terminated in `CX_SY_OPEN_SQL_DB` → `CX_CSP_ACT_INTERNAL` → `RAISE_SHORTDUMP` inside `CL_CSP_ACT_SAVE_TO_DB`, with the database reason naming a duplicate primary or unique secondary key. The different `DeliveryUUID` values are what make the evidence conclusive: the collision can only have been on the secondary business index. This was the open question the previous slice refused to guess at, and the answer is the less convenient one — RAP's `FAILED`/`REPORTED` machinery covers what the framework validates, not what the database refuses underneath it.

**A test whose proven outcome is a short dump cannot live in a regression suite.** The consequence is not that the constraint is wrong — it is the final persistence safety net and stays exactly as declared — but that verifying it is *manual infrastructure evidence*, not an automated assertion. A dump does not fail one test, it aborts the run and leaves every later assertion unexecuted, so a suite that provokes it on every pass tests less than a suite that does not. What the automated suite keeps is the **positive** form of the same invariant: after a successful create, exactly one intent exists for that order and revision. Neither of the two tempting escapes was taken — writing the duplicate with direct SQL would have bypassed the RAP rule the project exists to follow, and catching or suppressing the dump would have traded a real guarantee for a green line.

**`total etag` requires `with draft` on this target, so a non-draft BO cannot have one.** The first BDEF copied `lock master total etag LastChangedAt` from `ZJP_I_PurchaseOrder`, and ADT refused it: *"A `total etag` field can be flagged only if `with draft` is used."* The copy was the mistake, not the target: PurchaseOrder is draft-enabled and has a composition child, and a total etag exists to version a whole composition tree through a draft. DeliveryIntent is deliberately neither drafted nor composed, so it has nothing for a total etag to cover. The fix was to drop it to plain `lock master` and keep `etag master LocalLastChangedAt` — pointedly **not** to add `with draft` to satisfy the syntax, which would have changed the business object to suit its own etag declaration. `LastChangedAt` is still mapped and readonly; only its role as the *total* etag is gone. The general lesson: a declaration copied from a verified object carries that object's assumptions with it, and the ones that bite are the assumptions the source object satisfies invisibly.

**A `readonly` field with managed numbering cannot appear in a `CREATE FIELDS` list, and the compiler says so rather than the runtime.** The test tried to create a second intent supplying the first one's own `DeliveryUUID`, on the reasoning that the target's answer would be informative either way. ADT refused to compile it: *"The field `DELIVERYUUID` of entity `ZJP_I_DELIVERYINTENT` cannot be modified."* Three further errors — `MAPPED_DUP_KEY`, `FAILED_DUP_KEY` and `REPORTED_DUP_KEY` unknown — were only cascade: the statement never compiled, so its inline declarations never existed and every later reference to them dangled. Four errors, one cause, which is worth remembering when reading an ADT error list: fix the first real one and re-activate rather than fixing four things.

The substantive lesson is that the test contradicted a declaration the same slice had written. `field ( readonly, numbering : managed )` says nobody supplies this value, and the test then supplied it — an inconsistency that a careful read of the BDEF against the test's own field lists would have caught before activation. The correct response was to delete the statement, not to loosen the BDEF: the compiler error *is* the evidence the test was reaching for, and a stronger form of it. "A duplicate key is rejected" is a behaviour that must be observed and could regress; "a duplicate key cannot be expressed" is a property of the model. Loosening the declaration to make the test writable would also have required a UUID-creation API this project has never used and no probe has established, so the cheap-looking fix carried an unverified dependency.

**ABAP method names are limited to 30 characters, and a descriptive test name hits it easily.** `TEST_DELIVERY_INTENT_PERSISTENCE` is 32 and was rejected outright. It became `TEST_DLV_INTENT_PERSIST` at 23 — keeping "persist" on purpose, because the object inventory reserves `ZJP_CL_PO_DISPATCH_TEST` for dispatch behaviour and the name is where that scope boundary is visible. Worth checking the whole introduced surface rather than the one name the compiler happened to reach first: a single error only reports the first offender, so the useful response is a scan of every new method, inline declaration and parameter, not a single rename.

**A constraint that dumps cannot be used as control flow, which is a design requirement for a slice not yet written.** The physical unique index is the right last line of defence and the wrong first one. Because a violation reached during managed RAP save terminates the session rather than returning `FAILED`, `sendToSupplier` must never let a duplicate delivery intent reach the database: it has to check for an existing intent for that purchase order revision and **reuse** it, so a retry replays the delivery identity it already has instead of racing the constraint. The transaction-boundary sequence already said "refuse if a non-terminal intent already exists"; what the dump adds is that this check is not an optimisation or a nicety but the only thing standing between a retry and a terminated session. The general shape is worth keeping: a database constraint proves an invariant holds, and application logic has to make sure the proof is never needed.

## Phase 5.2c — a seam, a fake, and what a passing test does not prove

**Phase 5.2c is SAP runtime-verified.** `ZJP_IF_OUTBOUND_TRANSPORT`, `ZJP_CL_TRANSPORT_FAKE` and `ZJP_CL_TRANSPORT_TEST` activated and the harness ran to `PASS: Phase 5.2c outbound transport abstraction verified.` with no `STOP` and no short dump. The lessons below are what the slice actually taught, not a restatement of the design.

**An interface-typed reference is the test, not a detail of it.** Every scenario ran through `REF TO ZJP_IF_OUTBOUND_TRANSPORT`, with the concrete class named only at construction and never called through afterwards. That distinction is easy to write off as pedantry until you ask what a test proves when the variable is typed as the fake: only that a class with the right method names exists. Typed as the interface, the same run proves a consumer can dispatch to an implementation it does not name — which is the property the real HTTP transport will depend on when it replaces the fake without a caller changing. The harness is one small class, and this is the only reason it is worth having.

**A designed distinction becomes real the first time something executes it.** The interface returns an outcome rather than raising, so that "the receiver never answered" stays distinguishable from "the receiver answered with a failure". That was argued from API_CONTRACTS — *"a timeout never proves non-delivery"* — and the argument was sound, but it was still an argument. The run made it evidence: `409` came back `answered = X` and UNANSWERED came back `answered = false` with status `0`, and neither path needed an exception. Worth noticing that the 409 case is the one people get wrong, because a conflict *feels* like a failure; the interface refuses to let it be confused with a dead connection, and those two lead to opposite next actions.

**Byte equality is a sharper assertion than "both succeeded".** CAP answers an exact replay with the *stored original* receipt, so the fake returns the same body for `201` and `200` and the test asserts they are equal rather than merely both present. The assertion also came out stronger than intended: because the replay scenario constructs its own CREATED instance instead of reusing the previous test's result, byte equality across two independently built objects shows the determinism belongs to the class and not to one instance's history. Independence between test scenarios cost a few lines and bought a second guarantee.

**The first use of a language element in a project is unproven, even when it is core language.** The CONFLICT body check needed a containment test, and a grep showed no string-containment operator had ever been used in this repository. `CS` is core ABAP rather than a released API, so it was reasonable to write — but reasonable is not evidence, and it was flagged as unproven on this target before activation. **It compiled and executed correctly.** The habit is the point: the compiler is cheap to ask and the answer gets recorded, exactly as it was for `total etag` and the 30-character method-name limit, which were also things "everyone knows" until this system said otherwise.

**A green suite marks the boundary of what was tested, and the boundary deserves writing down.** The fake returns fixture identifiers rather than echoing the request, because correlating a receipt with the delivery sent requires JSON parsing that belongs to 5.2d and 5.2f. So four passing scenarios prove **outcome classification** and say nothing about **body correlation**. The fake also does not record the request it was given — a real gap for a future coordinator test, left open deliberately so the seam grows when a test demands it rather than in anticipation. Naming both limits in the same place as the passes is what stops a green run from being read as more than it is.

**A test object's name is where a scope boundary is visible, so a new slice can justify a new class.** 5.2c changes no RAP behavior, so the standing rule that `ZJP_CL_PO_EML_TEST` is extended whenever RAP behavior changes simply did not reach it; putting transport unit tests in an EML lifecycle regression suite would have made the suite's name inaccurate and coupled a seam test to a fixture chain it has no reason to touch. A dedicated `ZJP_CL_TRANSPORT_TEST` was the cheaper honesty, and it was added to the section 10 object inventory so it is a recorded decision rather than an undocumented exception — which is the same discipline that keeps `ZJP_CL_PO_DISPATCH_TEST` reserved for the 5.2g coordinator instead of quietly absorbing whatever needs a home first.

## Phase 5.2d — the builder, the mapper, and a fixture that proved more than intended

**Phase 5.2d is SAP runtime-verified.** `ZJP_CL_ORDER_DELIVERY_BUILDER`, `ZJP_CL_CAP_ORDER_MAPPER` and `ZJP_CL_BUILDER_TEST` activated and ran to `PASS: Phase 5.2d outbound builder and CAP mapper verified.`

**A text literal is limited to 255 characters, and a constant cannot be split.** The Phase 5.2d harness holds the golden CAP payload — 524 characters — as its expected value, and writing it as `CONSTANTS golden_body TYPE string VALUE '…'` was rejected: *"The text literal … is longer than 255 characters. Check whether it ends correctly."* The two halves of that limitation have to be taken together. A literal caps at 255, and a `CONSTANTS` `VALUE` must be a **single literal**, so `&&` is not available to work around it — which means a payload-sized fixture cannot be a constant at all on this target. It became a private method concatenating nine pieces, the longest 83 characters, split at JSON boundaries so each stays readable.

The lesson generalises past this one fixture: **any wire-shaped expected value will outgrow a constant**, and the CAP contract's bodies only get longer from here. The mapper was unaffected because it never holds a whole payload as a literal — it builds one member at a time — which is a small accidental argument for building JSON through a builder rather than assembling it from text.

It is worth checking the equivalence rather than trusting the split: the concatenation was verified to reproduce the original 524-character payload byte for byte and to still parse as JSON, because a fixture that quietly drifts from the golden value turns a passing test into a lie.

**The most valuable number in the run was a zero nobody chose.** The builder test picks whatever active order the database happens to offer, and the one it found carried **`OrderRevision = 0`** — a row persisted before Phase 5.2a, which P11 established keeps its original values because nothing was ever back-filled. The snapshot carried the `0` through unchanged, and that is **stronger** evidence than a `1` would have been. `1` is exactly what a builder that quietly recalculated the revision would also produce, so with a `1` the correct behaviour and the bug are indistinguishable; a `0` can only have been copied. The general point is worth keeping: a fixture whose expected value coincides with the most likely wrong value tests nothing, and the accident of an old row gave this test a discriminating case that a freshly created fixture would have destroyed. It is also an argument for testing against real persisted data rather than only against data the test made.

**Two independent test paths are a feature, and their numbers are allowed to disagree.** The builder runs against a real order; the mapper runs against a deterministic in-memory snapshot whose `revision` is `1`. Those two revisions differ because the tests answer different questions — one proves RAP read behaviour, the other proves byte-exact wire transformation, and a live order with generated identities can never give the second. Merging them into one "realistic" end-to-end fixture would have cost the byte comparison, which is the single strongest assertion in the slice.

**One byte comparison beats a page of field assertions.** The mapper's output was compared with the golden payload the P10 probe produced — the same shape the deployed CAP service accepted with 201. That one equality covers every member name, the nesting, the scalar types, all three decimal scales, the C36 UUID form, `revision` and `lineNumber` as JSON numbers, `00010` → `10` and `EA` → `PCE` at once, and **it cannot pass by accident**, which a field-by-field check can when an assertion is quietly omitted. The cost is that a failure needs the two strings printed side by side to diagnose, which the harness does.

**A rejection path deserves its own test, or "we do not guess" is only a comment.** The contract says *"unknown units fail validation; they are not guessed"*, and the implementation honours it with a lookup that can miss rather than an `IF`. Unit `BOX` returned `success = false`, `UNSUPPORTED_UNIT` and — the part worth asserting — an **initial** request, so a refused delivery cannot be mistaken for a sendable one. The negative test is what distinguishes a mapping that rejects from one that happens not to have been given a bad value yet.

**Explicit member names are worth the extra line each.** `XCO_CP_JSON`'s builder can derive camelCase from ABAP field names, and this mapper does not let it. The contract's names are case-sensitive, so an implicit rule is a silent failure waiting for the first field that does not round-trip — and passing the name to `ADD_MEMBER` puts the external wire contract in the source, where it cannot drift when someone renames an ABAP field.
