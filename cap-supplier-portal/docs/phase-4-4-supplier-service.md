# Phase 4.4 — supplier-facing service and supplier decisions

Status: **locally runtime-verified.** From a clean `node_modules`, `npm ci`, `npm run typecheck` and `npm test` all succeeded; **63 tests pass in 14 suites**, including every Phase 4.1, 4.2 and 4.3 test. All eight supplier scenarios were also exercised by hand against a running server. As in the earlier Phase 4 subphases this is local Node.js execution evidence, a different and weaker claim than the SAP runtime evidence behind Phases 1–3. Nothing here runs in or against an SAP system, no ABAP source was touched, and **no supplier decision is sent anywhere** — that is Phase 5.

## Purpose

Give a supplier a service of its own: see the orders it was sent, inspect the lines, and answer with an acceptance, a rejection or a revised delivery date. Each answer is recorded together with a pending outbound response that a later phase will deliver to SAP.

## Service boundary

`SupplierService` is separate from `IntegrationService`, because the callers are different in kind — one is a machine delivering snapshots, the other is a person deciding about them — and they will carry different authentication and permissions (ADR-005).

| Property | Value |
| --- | --- |
| Declaration | `@protocol: 'rest'`, `@path: '/rest/supplier/v1'`, `@requires: 'authenticated-user'` |
| Reads | `@readonly` projections, narrowed by a row filter |
| Writes | **None.** Every change is an explicit bound action |
| Persistence exposure | Projections with explicit element lists; no FK column, no SAP correlation field |

ARCHITECTURE.md draws exactly this line: *"Generated READ support is appropriate with authorization filters; ingestion and decisions require custom handlers, not unrestricted generic CRUD."* So reads are generated by CAP and scoped by a hook, and every decision has a handler. There is no writable path to `status`, `rejectionReason` or `responseVersion` anywhere in the service.

## Exact routes

| Method | Route | Result |
| --- | --- | --- |
| `GET` | `/rest/supplier/v1/Orders` | the caller's own orders |
| `GET` | `/rest/supplier/v1/Orders/{portalOrderId}` | one of the caller's own orders |
| `GET` | `/rest/supplier/v1/Orders/{portalOrderId}/items` | that order's lines |
| `GET` | `/rest/supplier/v1/OrderItems` | all the caller's lines, scoped |
| `POST` | `/rest/supplier/v1/Orders/{portalOrderId}/accept` | accept |
| `POST` | `/rest/supplier/v1/Orders/{portalOrderId}/reject` | reject with a reason |
| `POST` | `/rest/supplier/v1/Orders/{portalOrderId}/updateEstimatedDeliveryDate` | revise the date |
| `PATCH` / `DELETE` | any of the above | **405** |

These are the paths the boundary table in [API_CONTRACTS.md](../../API_CONTRACTS.md) specifies, reproduced exactly. CAP's REST adapter routes a **bound action** as `POST /<service-path>/<EntitySet>/<key>/<actionName>` with the parameters as the JSON body, which is precisely the documented shape — nothing in the external contract had to move.

## Supplier identity, and what it is not

The supplier behind a request comes from the **authenticated user's attributes**:

```ts
const code = req.user?.attr?.supplier
```

ARCHITECTURE.md requires this and rules out the alternative in the same sentence: *"Supplier identity comes from authenticated user attributes or an explicit local mock-user mapping, never a trusted supplier code supplied by the browser."* No route, body or query parameter in this service accepts a supplier code.

Locally that mapping is CAP's mocked authentication in `.cdsrc.json`:

| User | Password | `supplier` attribute |
| --- | --- | --- |
| `supplier1` | `supplier1` | `SUP001` |
| `supplier2` | `supplier2` | `SUP002` |
| `nosupplier` | `nosupplier` | *(none)* |

**This is local supplier isolation, not production authentication.** Mocked basic auth over HTTP on a developer machine proves that the isolation *logic* is correct and enforced server-side; it proves nothing about identity assurance. XSUAA, IAS, token validation and role collections are Phase 8 and are deliberately absent. The third user exists so the "authenticated but not a supplier" path is a tested outcome rather than an assumption.

## Row-level isolation

Two hooks, applied before anything reads:

```ts
this.before('READ', 'Orders', req => this.scopeOrders(req))
this.before('READ', 'OrderItems', req => this.scopeItems(req))
```

`scopeOrders` adds `supplierCode = <caller>` to the query CAP is about to run; `scopeItems` restricts items to orders belonging to the caller, via a subquery. Because the filter is added to the query itself rather than applied to a result, it covers the collection, a single order addressed by key, `$expand` and navigation with one rule each.

The decision actions do not rely on those hooks. Each one re-reads the order with `{ ID: portalOrderId, supplier_ID: supplier.ID }`, so ownership is a condition of the load, not a check that could be forgotten after it.

**Knowing another supplier's order id is not enough.** A foreign id is answered `404` with no body fields, which is the *"access denied or scoped not-found response; no fields disclosed"* outcome the design acceptance cases describe. 404 was chosen over 403 deliberately: a 403 would confirm that the id exists and belongs to someone else, which is itself a disclosure.

| Case | Result |
| --- | --- |
| SUP001 lists orders | `PO00001001`, `PO00001002` |
| SUP002 lists orders | `PO00001003` |
| SUP001 reads its own order | 200 |
| SUP001 reads SUP002's order by id | **404**, no fields |
| SUP001 reads items of SUP002's order | **404** |
| SUP001 reads `/OrderItems` | 3 lines, all its own |
| Anonymous | **401** |
| Authenticated, no supplier attribute | **403** `NO_SUPPLIER_IDENTITY` |

## Read model

An explicit element list, not the table.

**Order:** `portalOrderId`, `supplierCode`, `externalOrderNumber`, `status`, `currency`, `totalAmount`, `estimatedDeliveryDate`, `rejectionReason`, `responseVersion`, `receivedAt`, `items`.

**Item:** `ID`, `portalOrderId`, `lineNumber`, `productCode`, `description`, `quantity`, `uom`, `unitPrice`, `currency`, `lineAmount`.

Omitted on purpose: `sourceSystem`, `sourceOrderId`, `sourceRevision`, `deliveryId`, `modifiedAt`, `supplier_ID`, `order_ID`, `sourceItemId`. Those are SAP correlation and portal bookkeeping; a supplier acts on none of them. A test asserts each one is absent, so a future projection change cannot quietly widen the surface.

Two element choices are worth explaining. `supplierCode` **is** exposed: the row filter must be expressible over the projection's own elements, and it tells the caller nothing it did not already authenticate as. The item's parent key is exposed as `portalOrderId` rather than `order_ID` — the same id under the public name, so the composition resolves without publishing a foreign-key column.

## Decisions

All three commands share a shape: a stable `responseId`, a version precondition, and whatever the decision needs.

### accept

```json
{ "responseId": "<uuid>", "expectedResponseVersion": 0, "estimatedDeliveryDate": "2026-09-30" }
```

Requires status `RECEIVED`. The date is **optional** — *"an omitted date means unknown"* — and is never defaulted to today. Sets status `ACCEPTED`.

### reject

```json
{ "responseId": "<uuid>", "expectedResponseVersion": 0, "reason": "Out of stock until Q1" }
```

Requires status `RECEIVED` and a non-blank reason of at most 255 characters. *"Rejection requires a reason and forbids a delivery date"*, so `reject` takes no date parameter at all rather than accepting one and validating it away. Sets status `REJECTED`.

### updateEstimatedDeliveryDate

```json
{ "responseId": "<uuid>", "expectedResponseVersion": 1, "estimatedDeliveryDate": "2026-12-20" }
```

Requires status `ACCEPTED`. *"A date update keeps decision ACCEPTED and increments the version."* The date is mandatory here.

### Date rule

*"A newly supplied date cannot be earlier than the date portion of request receipt in UTC."* Compared as calendar dates, so today passes and yesterday does not. Replay detection runs **before** this check, because *"historical dates are not rejected when the exact earlier request is replayed: deduplication runs before current-date validation"* — a replayed command whose date has since passed still succeeds.

### Result

```json
{
  "portalOrderId": "22222222-2222-4222-8222-000000000001",
  "externalOrderNumber": "PO00001001",
  "status": "ACCEPTED",
  "responseVersion": 1,
  "estimatedDeliveryDate": "2026-09-30",
  "rejectionReason": null,
  "respondedAt": "2026-09-16T22:55:49.779Z",
  "responseDeliveryStatus": "PENDING"
}
```

`responseDeliveryStatus` is always `PENDING` in Phase 4.4 and is the contract's way of saying the decision is committed here and **not** yet known to SAP: *"UI acceptance does not claim SAP has been updated."* A test pins the key set.

## responseVersion

Starts at `0` and is incremented by the portal on every accepted command — *"CAP assigns the next responseVersion atomically"*. Each command must carry `expectedResponseVersion`, and a mismatch is refused: *"New IDs with stale/conflicting versions return 409 and require reconciliation, never overwrite newer state."*

The precondition is **required**, not optional. Making it optional would let a client skip the one mechanism that stops a stale decision overwriting a newer one, and the contract names it as the mechanism rather than as a suggestion. 409 was chosen over 412 because the contract states the code explicitly for version conflicts, even though 412 is also defined for stale preconditions.

Order of checks matters and is contract-driven:

```text
identity → order ownership → REPLAY by responseId → version precondition → lifecycle → content
```

Replay is first because *"replay detection must recognize an already successful identical command even if its original version is now stale"*. A retried command whose version has moved on must still succeed; only a *new* command is held to the precondition.

## Replay and conflict

`responseId` is the caller's idempotency key.

| Case | Result |
| --- | --- |
| Same `responseId`, same content | **200** with the original decision; nothing new recorded |
| Same `responseId`, different content | **409** `RESPONSE_PAYLOAD_CONFLICT`; the stored decision is unchanged |

This is *"a duplicate response ID with the same content is a no-op; the opposite decision is a conflict"*, enforced by a `UNIQUE (responseId)` constraint and a content comparison.

## Pending outbound response

`SupplierResponseDeliveries` is the record a Phase 5 sender will read.

Specified in the CAP persistence table of [domain-model.md](../../docs/architecture/domain-model.md) as *"responseId: UUID; order association; version; immutable response payload; state PENDING/DELIVERED/FAILED/UNKNOWN; attempt count; last error; timestamps"*. **That table marks it phase 5, and Phase 4.4 pulls forward only what a decision needs**: the identity, the version, the payload and the state. Attempt count, last error and the sender itself stay in Phase 5, because nothing in Phase 4 ever attempts a delivery — every row written here is `PENDING` and stays `PENDING`. The same judgement was applied to `DeliveryReceipts` in Phase 4.3, and recorded the same way.

Two database constraints come with it:

```sql
CONSTRAINT pih_portal_SupplierResponseDeliveries_responseId   UNIQUE (responseId)
CONSTRAINT pih_portal_SupplierResponseDeliveries_orderVersion UNIQUE (order_ID, version)
```

The second is the documented `responses(order, version)` rule, and it turns out to do double duty — see the atomicity test below.

## Transaction boundary

One request, one transaction, two writes:

```text
UPDATE Orders  SET status, estimatedDeliveryDate, rejectionReason, responseVersion, modifiedAt
INSERT SupplierResponseDeliveries (responseId, order, version, payload, state = PENDING)
```

*"Persist each decision and its pending response in the same CAP transaction."* An order can never be `ACCEPTED` with no pending response, nor hold a pending response while still `RECEIVED`.

Every refusal test asserts this rather than assuming it: a shared helper snapshots the order row and the response count, issues the command, and asserts both are unchanged afterwards.

### The atomicity test is a real failure, not a simulation

Stating that CAP uses transactions proves nothing. The test forces the **second** write to fail after the first has already run:

1. A response row for `(order, version 1)` is planted directly, taking the slot the next decision will need.
2. The supplier accepts the order with `expectedResponseVersion: 0`.
3. The handler updates the order to `ACCEPTED` with `responseVersion: 1` — this write succeeds.
4. It then inserts its own response at version 1, which violates `UNIQUE (order_ID, version)`.
5. The transaction rolls back.

The test then asserts the order is still `RECEIVED`, still version `0`, still with no date, and that only the planted row exists. Nothing about this is artificial: the constraint is the one the domain model specifies, and the failure happens after the order row has already been written inside the same transaction.

## HTTP and error semantics

| Situation | Status | Code |
| --- | --- | --- |
| Successful decision or replay | **200** | — |
| Anonymous | **401** | framework |
| Authenticated without a supplier attribute | **403** | `NO_SUPPLIER_IDENTITY` |
| User maps to an unknown or inactive supplier | **403** | `UNKNOWN_SUPPLIER_IDENTITY` |
| Order absent, or belonging to another supplier | **404** | `ORDER_NOT_FOUND` |
| Missing or malformed `responseId` | **400** | `MISSING_RESPONSE_ID` |
| Missing version precondition | **400** | `MISSING_VERSION_PRECONDITION` |
| Missing or blank rejection reason | **400** | `MISSING_REJECTION_REASON` |
| Rejection reason over 255 characters | **400** | `REJECTION_REASON_TOO_LONG` |
| Malformed delivery date | **400** | `INVALID_DELIVERY_DATE` |
| Delivery date before today (UTC) | **400** | `DELIVERY_DATE_IN_PAST` |
| Stale version precondition | **409** | `STALE_RESPONSE_VERSION` |
| Accept or reject on an already decided order | **409** | `INVALID_STATE_FOR_DECISION` |
| Date update on an order never accepted | **409** | `INVALID_STATE_FOR_DATE_UPDATE` |
| Same `responseId`, different content | **409** | `RESPONSE_PAYLOAD_CONFLICT` |
| Generic write attempt | **405** | framework |

Thirteen application-defined codes, all in the contract envelope with `code`, `message`, `correlationId` and `retryable`.

### A Phase 4.3 lesson applied in advance

Action parameters are declared **without** `not null`, deliberately. CAP's own `ASSERT_MANDATORY` check runs before any handler and answers in the framework's envelope — so with `not null`, a missing `reason` produced `ASSERT_MANDATORY` and `MISSING_REJECTION_REASON` would have been unreachable code, exactly as `INVALID_PAYLOAD` turned out to be in Phase 4.3. That was caught here during implementation rather than after, by trying it. Requiredness is enforced in the handler instead, so every supplier-facing 400 is a documented code in a consistent envelope.

## OI-04

**Closed by runtime evidence, not by code inspection.** Phase 4.3 proved REST structured ingestion; the remaining half was the supplier bound-action wire behaviour, and that is now executed and recorded above.

The concrete answer: CAP's REST adapter routes a bound action as **`POST /<service-path>/<EntitySet>/<key>/<actionName>`**, with the action's parameters as a flat JSON object in the request body and the action's `returns` type as the JSON response body. The instance is addressed by the URL key — here `portalOrderId`, reachable in the handler as `req.params[0]` — and never by a parameter. That matches the paths API_CONTRACTS.md specified, so the documented supplier routes are the real ones.

## Known limitations

- **Mocked authentication.** Basic auth against users in `.cdsrc.json`. Isolation logic is enforced server-side and tested; identity assurance is not addressed. XSUAA/IAS is Phase 8.
- **No concurrency was raced.** The version precondition is verified sequentially: a stale version is refused and a replay succeeds. Two genuinely simultaneous decisions on one order were not exercised, and the same local-SQLite serialization noted in Phase 4.3 applies. The `UNIQUE (order_ID, version)` constraint is what would hold the invariant, and it is proven to fire — that is how the atomicity test works — but the concurrent path itself is reasoned.
- **Nothing is sent.** No sender, no retry, no scheduler, no `responseDeliveryStatus` other than `PENDING`. The Phase 5 sender will read these rows.
- **Attempt count and last error are absent** from the response entity; they belong to the sender.
- **`supplierCode` is exposed** on the order read model. It is the caller's own code, needed so the row filter is expressible over the projection, and it discloses nothing new.
- **No pagination.** API_CONTRACTS.md requires bounded pagination for lists and defers the exact parameters; with three fixture orders this was not implemented and remains open for the supplier UI in Phase 4.5.

## What remains for Phase 4.5

A minimal supplier UI over this service: list the supplier's orders, open one and inspect its lines, and submit accept, reject or a date revision. The service is UI-ready — it is authenticated, scoped and returns stable shapes — so 4.5 adds a front end and the pagination the list will need, not new business rules.

## Reading the Phase 4.4 code if CAP is new to you

**Service projection versus db entity.** `db/schema.cds` defines `pih.portal.Orders`, the table. `srv/supplier-service.cds` defines `SupplierService.Orders`, a *projection* — a view with an explicit element list, renamed keys and no FK columns. The supplier never addresses the table. Phase 4.3's `IntegrationService.Orders` was not a projection at all but a standalone contract shape; here a projection is right, because the supplier really is reading stored rows, whereas the integration client was posting a differently-shaped message.

**Row isolation with `this.before`.** `this.before('READ', 'Orders', …)` runs before CAP's generated read and adds a condition to the query object itself:

```ts
req.query.where({ supplierCode: supplier.supplierCode })
```

Because the filter goes into the query rather than onto the result, one rule covers the collection, a single key, `$expand` and navigation. `before` augments the framework's behaviour; `on` (used in Phase 4.3) replaces it.

**Request and user context.** `req.user` is CAP's authenticated user. `req.user.attr.supplier` is an attribute attached to that user — from mocked config locally, from an identity provider later. The handler reads the caller's identity from the framework, never from the payload. The nearest RAP parallel is `sy-uname` plus an authorization object, except that the attribute here is an explicit part of the user model.

**Bound actions.** `accept`, `reject` and `updateEstimatedDeliveryDate` are declared inside the entity's `actions { … }` block, which makes them *bound*: they always operate on one instance, and the URL carries that instance's key. The handler reads it as `req.params[0].portalOrderId`, and reads the parameters as `req.data`. This is the same idea as the RAP actions in Phase 2 — `submit`, `approve`, `reject`, `cancel` were also bound to a root instance and took their parameters separately.

**Why the supplier cannot simply `PATCH status`.** It is not merely blocked; it is not modelled. The projections are `@readonly`, so `PATCH` and `DELETE` return 405, and `status` appears in the read model only as an output. A status field a client can write is a status with no rules: nothing would enforce `RECEIVED → ACCEPTED`, nothing would require a reason with a rejection, nothing would allocate a version, and nothing would write the pending response. Making the transition an action means the rule and the write cannot be separated. This is exactly what Phase 2.7C established in RAP — *"No unrestricted status PATCH exists"* — reappearing on the CAP side.

**Transactions.** The `UPDATE` and the `INSERT` in `persist` run inside the request's transaction automatically. There is no commit call; throwing or rejecting rolls back. The atomicity test exists because that guarantee is worth demonstrating rather than asserting.

**`responseVersion`.** A plain integer that the portal owns. The client sends the version it believes is current; if the order has moved on, the command is refused instead of overwriting a newer decision. It is an optimistic-locking token expressed in the business model rather than an HTTP ETag — the contract chose it that way, so the same value can travel to SAP in the response payload, which an ETag could not.

**The pending outbound response.** A row recording what the supplier decided, waiting for a sender that does not exist yet. Writing it in the same transaction as the decision is what makes "the supplier decided" and "SAP will be told" a single fact rather than two that can drift apart.
