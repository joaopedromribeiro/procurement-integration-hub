## Projection behavior definition

Generated by ADT and activated. It is used verbatim; none of it was hand-written.

```
projection;

strict ( 2 );

use draft;

define behavior for ZJP_C_PurchaseOrder
{
  use create;
  use update;
  use delete;
  use action removeItem;
  use action submit;
  use action approve;
  use action reject;
  use action cancel;
  use action Edit;
  use action Activate;
  use action Discard;
  use action Resume;
  use action Prepare;
  use association _Items { create; with draft; }
}

define behavior for ZJP_C_PurchaseOrderItem
{
  use update;
  use association _PurchaseOrder { with draft; }
}
```

Three things in that source are worth reading deliberately:

- **`use draft;`** is what makes the technical draft reachable from OData at all. Phase 2 verified the draft through EML; until this line existed, no external consumer could see `IsActiveEntity`, `HasActiveEntity` or the framework draft actions.
- **The child block has no `use delete;`.** The base item declares `internal delete`, so item removal stays behind the root action `removeItem` exactly as Phase 2.6 designed it. An OData client cannot delete an item directly.
- **`use delete;` on the root is safe** because Phase 2.7D-2's `delete ( precheck )` still fires underneath. The projection re-exposes the operation; it does not re-open the rule.

The child projection's missing `provider contract transactional_query` — the documented Phase 1 compatibility adjustment — did **not** block service exposure. That was the highest-risk unknown going into this subphase, and the target answered it: root contract plus redirected-to-parent child is a working combination for a transactional OData V4 service here. Do not "fix" the child by restoring the clause the compiler rejected.

## Service definition and binding

The activated service definition source, used verbatim:

```
@EndUserText.label: 'Purchase Order UI Service'
define service ZJP_UI_PURCHASEORDER {
  expose ZJP_C_PurchaseOrder     as PurchaseOrders;
  expose ZJP_C_PurchaseOrderItem as PurchaseOrderItems;
}
```

| Setting | Value |
| --- | --- |
| Service definition | `ZJP_UI_PURCHASEORDER` |
| Exposed entity | `ZJP_C_PurchaseOrder` as `PurchaseOrders` |
| Exposed entity | `ZJP_C_PurchaseOrderItem` as `PurchaseOrderItems` |
| Service binding | `ZJP_UI_PURCHASEORDER_O4` |
| Binding type | OData V4 – UI |
| Service version | `0001` |

Service root as published on the current development target:

```text
https://s4h2023.sapdemo.com:44323/sap/opu/odata4/sap/zjp_ui_purchaseorder_o4/srvd/sap/zjp_ui_purchaseorder/0001/?sap-client=100
```

The host, port and client identify one development system rather than a stable contract. The durable identity is the pair of object names; resolve the host per environment.

**Publishing required a detour that is worth recording.** Client 100 on this target is a Customizing client, so local publishing from ADT was refused. The service group was published successfully through transaction **`/IWFND/V4_ADMIN`** instead. This is an environment property, not a modelling error, and anyone reproducing the project on a Customizing client will meet it.

This is the **buyer UI service only**. [API_CONTRACTS.md](../../API_CONTRACTS.md) describes a second, separate RAP surface for `applySupplierResponse`; that integration service belongs to Phase 5 and was deliberately not created.

## Runtime evidence

The learner exercised the endpoint and reported the following. No independent SAP or HTTP execution is claimed here.

### Metadata surface

| Check | Result |
| --- | --- |
| Service document | Works |
| `$metadata` | Works |
| `PurchaseOrders`, `PurchaseOrderItems` | Both exposed |
| Draft metadata | Exposed |
| Bound business actions | `submit`, `approve`, `reject`, `cancel`, `removeItem` |
| Draft actions | `Edit`, `Activate`, `Discard`, `Resume`, `Prepare` |
| `reject` parameter | `RejectionReason` |
| `removeItem` parameter | `PurchaseOrderItemUUID` |
| `PurchaseOrderNumber` | Exposed as computed / read-only |
| `_Items` navigation | Works through `$expand` |

Both action parameters reached the OData surface from their abstract entities — `ZJP_A_Reject` and `ZJP_A_RemoveItem` — with no redeclaration in the projection behavior definition.

### Reads and bound actions

| Case | Result |
| --- | --- |
| `GET` active `PurchaseOrders` | PASS |
| `GET` with `$expand=_Items` | PASS |
| `approve` via `POST`, `SUBMITTED` → `APPROVED` | PASS |
| `approve` again on the `APPROVED` order | HTTP 400, `Only submitted orders can be decided.` — PASS |
| `reject` with parameter, `SUBMITTED` → `REJECTED` | `RejectionOrigin = APPROVER`, `RejectionReason = "Rejected via OData test"` — PASS |

**The Phase 2 message texts arrive unchanged at the HTTP boundary.** `Only submitted orders can be decided.` is the exact string the Phase 2.7C handler emits and the console test asserts. The action handler is the single enforcement point for EML and OData alike; nothing was duplicated at the service layer.

### Draft lifecycle

| Case | Result |
| --- | --- |
| `Edit` an active `DRAFT` order | PASS; draft returned with `IsActiveEntity = false`, `HasActiveEntity = true` |
| `PATCH` draft `PurchasingGroup` `001` → `002` | PASS |
| Active instance before activation | Still `001` — PASS |
| `Activate` | PASS; active became `002`, draft disappeared |
| `Edit`, `PATCH` `002` → `003`, then `Discard` | Active remained `002`, draft disappeared — PASS |

### Creation through to submission

| Step | Result |
| --- | --- |
| `POST PurchaseOrders` | Created a technical draft; `Status` initialized to `DRAFT`; `PurchaseOrderNumber` blank |
| `POST` through `_Items` | Item created, `Quantity = 2`, `NetPrice = 750` |
| Item `TotalAmount` | Calculated as 1500 |
| Header `TotalAmount` | Recalculated as 1500 |
| `Activate` | PASS; active order still `Status` `DRAFT` with a blank `PurchaseOrderNumber` |
| `submit` | HTTP 204 |
| Subsequent `GET` | `Status = SUBMITTED`, `PurchaseOrderNumber = PO00000010`, `TotalAmount = 1500` |

This is the Phase 2.7E rule observed from outside the system: the number appears at submission and not one step earlier. `Activate` ends the editing session and leaves the order in business `DRAFT` with no number; `submit` is what allocates.

### Post-submission immutability

| Step | Result |
| --- | --- |
| `Edit` on a `SUBMITTED` order | Allowed; a technical draft was created |
| That draft's inherited values | `Status = SUBMITTED`, `PurchaseOrderNumber = PO00000010` |
| `PATCH PurchasingGroup` on the draft | HTTP 400, `Only draft orders can be changed.` |
| Active order | Unchanged |
| `Discard` | Removed the technical draft — PASS |

`Edit` succeeding on a submitted order is **not** a hole. Phase 2.7B established that a draft taken from a submitted order carries that order's business status, and the prechecks resolve `%tky` against the draft row. The consumer can open an editing session; the first content change is refused. Phase 3.1 now shows this is equally true over HTTP, and adds that the draft inherits the allocated `PurchaseOrderNumber` too.

## Observed gaps, recorded rather than fixed

- **`__OperationControl` reports actions as available even when the lifecycle would reject them.** This is a UX shortcoming, **not a business-rule defect**: the RAP handlers still enforce every transition, as the HTTP 400 responses above show. Dynamic feature control could align the advertised operations with the current status, but it is out of scope and must not be implemented unless explicitly scoped. Phase 2.7B already recorded why feature control is UX only and never an enforcement layer — it is advisory and `IN LOCAL MODE` bypasses it.
- **`OptimisticConcurrency` appears in the metadata, but stale-ETag and multi-user behavior remain unproven.** Nothing in this subphase exercised a conflicting write. This is the open Phase 3 test item tracked as OI-13 and must not be reported as working.

## Source-control gap

The projection behavior definition and the service definition are both in the repository as activated source. Two gaps remain, one permanent and one tracked.

- **`ZJP_UI_PURCHASEORDER_O4` has no plain-text source form**, so no artifact was invented for it. Its settings and the `/IWFND/V4_ADMIN` publishing route are recorded above; that is the whole record a binding can have here.
- The draft tables **`zjp_po_hd`** and **`zjp_po_id`** are still referenced by the base behavior definition without repository source. That is the standing OI-10 export gap, unchanged and not specific to this subphase.

The service root and the full buyer-service contract are recorded in [API_CONTRACTS.md](../../API_CONTRACTS.md), which no longer describes that surface as merely proposed.
