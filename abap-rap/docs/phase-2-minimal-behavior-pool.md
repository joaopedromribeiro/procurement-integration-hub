## Purpose and flow

Create one behavior pool with one root authorization callback. The BDEF already declares instance authorization; this class fulfils the implementation requirement while managed RAP continues to own CRUD and saving.

```text
RAP instance-authorization request
  -> ZBP_I_PURCHASEORDER / lhc_PurchaseOrder
  -> read existing roots through EML in local mode
  -> return requested permissions under the permissive study policy
  -> RAP uses the result when processing the BO request
```

The policy deliberately allows the target-supported requested root update and delete permissions. It is a learning stub, not an authorization-object or role check. Do not present it as production business authorization. No global authorization, CDS read policy, state restriction, action, validation, determination or draft logic is added.

## Read the code

`PUBLIC ABSTRACT FINAL FOR BEHAVIOR OF` identifies the global behavior pool. The ABAP framework invokes its handlers. Neither a constructor nor an application entry point is needed.

`lhc_PurchaseOrder` inherits CL_ABAP_BEHAVIOR_HANDLER. `FOR INSTANCE AUTHORIZATION ... FOR PurchaseOrder` binds this method to the root alias declared in the BDEF. RAP derives the parameter types; use the target system's generated signature. The method also has framework response parameters such as failed and reported. See [SAP instance authorization](https://help.sap.com/docs/abap-cloud/abap-rap/implementing-instance-authorization).

The small `READ ENTITIES` statement reads root identities from the BO's transactional view. `IN LOCAL MODE` is internal access to the same BO and bypasses access controls for this read; it avoids recursively calling the authorization being implemented. It is not a way to bypass authorization for external callers. `CORRESPONDING #( keys )` transfers the input identities into the RAP read request. This internal read is necessary to distinguish existing and missing instances; it introduces no EML consumer program or CRUD exercise. See [SAP EML](https://help.sap.com/docs/abap-cloud/abap-rap/entity-manipulation-language-eml).

Read failures and messages are forwarded through failed/reported. Only successfully read roots receive permission results. Sorting and deduplicating the internal result table ensures one permission result per existing identity, even when input keys repeat. `DELETE ADJACENT DUPLICATES` changes this internal table only; it does not delete a purchase order. These choices follow the [SAP authorization implementation contract](https://help.sap.com/docs/ABAP_PLATFORM_NEW/fc4c71aa50014fd1b43721701471913d/9f462b619fd94e05a6498b356853e491.html).

`%tky` correlates each result with its RAP transactional key. `requested_authorizations` contains request flags; `if_abap_behv=>mk-on` means a permission was requested. `if_abap_behv=>auth-allowed` is the response value. Request flags and authorization decisions are different concepts, even if their technical representations look similar. Unrequested result fields stay initial. Clearing the result work area inside the loop prevents values from leaking between orders.

The target-generated structures do not expose a separate association-permission component for this handler; that block was removed. Dependent item update/delete use the root’s update authorization through _PurchaseOrder. Root CREATE and CDS read authorization remain separate concerns. The EML test will exercise composition creation without inventing unsupported authorization fields.

The framework still manages standard CRUD, the transaction buffer, persistence saving, declared UUID numbering, audit fields and locks. There is no custom saver, manual database write, COMMIT WORK or business calculation. Future authorization should replace the permissive assignments with decisions based on actual business permissions; introducing a policy/helper framework now would obscure this small learning step.
