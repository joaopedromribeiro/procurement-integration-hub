## Behavior Definition versus Behavior Implementation

The BDEF declares which operations exist and how RAP must process them: managed persistence, locks, field controls, associations and authorization ownership. It is written in Behavior Definition Language. Declaring instance authorization creates an obligation to provide an authorization implementation.

The Behavior Implementation is ABAP code in a special global class called a **behavior pool**. It is tied to the root BO and contains local handler classes for custom behavior callbacks. RAP invokes these callbacks; application callers request BO operations rather than instantiate handlers themselves. ZBP_I_PURCHASEORDER is needed now because the root declares instance authorization. Later validations, determinations and actions can use the same implementation infrastructure, but none is introduced here. See [SAP handler classes](https://help.sap.com/docs/latest/fc4c71aa50014fd1b43721701471913d/da411ea839d442369388c4ee78f3c734.html).

## How the entities and handlers relate

```text
Behavior Definition: ZJP_I_PURCHASEORDER
  PurchaseOrder     -> ZJP_PO_H; authorization and lock master
  PurchaseOrderItem -> ZJP_PO_I; authorization and lock dependent
          |
          | implementation in class
          v
Behavior pool: ZBP_I_PURCHASEORDER
  lhc_PurchaseOrder
    get_instance_authorizations (required custom callback)
  lhc_PurchaseOrderItem
    no custom callback required for the current child contract
```

Names beginning with `lhc_` are a local handler convention. Handler classes inherit from CL_ABAP_BEHAVIOR_HANDLER. Their RAP method signatures bind callbacks to the entity alias, such as PurchaseOrder; the class name alone does not establish that binding. They are local classes within the behavior pool, usually shown in ADT's Local Types area, not separate global class repository objects.

One local handler per entity is a useful organization as logic grows. The minimum implementation currently needs only the root handler. An empty child handler generated by ADT is harmless, but a separate child authorization implementation or second global behavior pool is unnecessary for this dependent child contract.

Managed CRUD means we do **not** write INSERT, UPDATE or DELETE statements against the persistence tables in these handlers. We also do not add a custom saver, unmanaged save, or COMMIT WORK. Those would change the responsibility split and are unnecessary here. Adding an authorization callback does not change the BO into an unmanaged implementation. See [SAP managed standard behavior](https://help.sap.com/docs/ABAP_PLATFORM_NEW/fc4c71aa50014fd1b43721701471913d/a44909694d6d47ea8d4583f91e588548.html).

## What get_instance_authorizations does

This is the conventional ADT-generated name for a method declared FOR INSTANCE AUTHORIZATION. It receives the keys of existing root instances and requested_authorizations flags identifying the permissions the caller needs. It returns a result correlated with those keys, explicitly marking the requested permissions as allowed or unauthorized. The generated signature is the target-system contract; use ADT's quick fix instead of guessing its parameters.

The target-generated root authorization structures expose update and delete permissions. The local handler implements those flags only; the previously proposed association-permission component was rejected by this SAP compiler and removed. The callback decides permissions without saving orders. Generated components must be checked in ADT rather than copied from a generic example.

Instance authorization concerns existing instances. It does not authorize standalone root CREATE, which has no existing order instance; global authorization is the separate mechanism for that concern. It also does not implement CDS read authorization. Neither global authorization nor DCL is added in this step.

## Why authorization belongs to the root

An item belongs to its order, so the order is the natural permission boundary. The _PurchaseOrder association lets RAP resolve an item's authorization master. For a dependent child's standard update/delete and create-by-association operations, RAP uses the authorization master's UPDATE permission. In particular, deleting an item is authorized as changing the order; it is not automatically the same permission as deleting the header. Do not assume a separate _Items permission component is available in this handler: the target compiler rejected it. Composition creation remains declared in the BDEF and will be exercised through EML. See [SAP authorization definition](https://help.sap.com/docs/ABAP_PLATFORM_NEW/fc4c71aa50014fd1b43721701471913d/2a26db5640364b46b843dca786c495d1.html).

Authorization and locking have different jobs despite sharing a parent: authorization decides permission; the lock coordinates concurrent modifications. Neither replaces the other. Future authorization policy should evaluate business permissions such as an authorized purchasing organization; business status/editability rules need deliberate modeling too.
