Current checkpoint: **Phase 5.2e is SAP runtime-verified** — SAP posts to the deployed CAP portal over real HTTP through the verified seam: [zjp_cl_outbound_transport.clas.abap](classes/zjp_cl_outbound_transport.clas.abap) and its real-network harness [zjp_cl_http_transport_test.clas.abap](classes/zjp_cl_http_transport_test.clas.abap) returned 201, an idempotent 200 with the identical receipt, and a 409 conflict with the receiver body intact, and classified an unresolvable destination as a technical failure. **Phase 5.2f, `sendToSupplier`, is next and is not started.** Below it, **Phase 5.2d is SAP runtime-verified** — the outbound builder [zjp_cl_order_delivery_builder.clas.abap](classes/zjp_cl_order_delivery_builder.clas.abap), the CAP mapper [zjp_cl_cap_order_mapper.clas.abap](classes/zjp_cl_cap_order_mapper.clas.abap) and the harness [zjp_cl_builder_test.clas.abap](classes/zjp_cl_builder_test.clas.abap). The builder read a real active order and wrote nothing; the mapper produced the golden CAP payload byte for byte, twice, and refused an unmapped unit. Below it, **Phase 5.2c is SAP runtime-verified** — the transport seam [zjp_if_outbound_transport.intf.abap](interfaces/zjp_if_outbound_transport.intf.abap), its network-free fake [zjp_cl_transport_fake.clas.abap](classes/zjp_cl_transport_fake.clas.abap) and the console harness [zjp_cl_transport_test.clas.abap](classes/zjp_cl_transport_test.clas.abap) all activated, and the harness passed CREATED `201`, REPLAYED `200` with a byte-identical receipt, CONFLICT `409` and UNANSWERED, every scenario driven through `REF TO ZJP_IF_OUTBOUND_TRANSPORT` with no network, no exception and no commit. The path-ownership split behind 5.2e — a path-less base destination for host, TLS and OAuth, with the route carried in the request — is recorded in [section 9.2](docs/phase-5-1-outbound-foundation.md). Below it, **Phase 5.2a and Phase 5.2b are SAP runtime-verified**: `submit` writes `OrderRevision = 1` and `initializeStatus` writes `IntegrationStatus = 'NOT_REQUESTED'`, and the `DeliveryIntent` stack exists — [zjp_po_dlv.ddl](persistence/zjp_po_dlv.ddl) with its unique Table Index `ZJP_PO_DLV~REV`, [zjp_i_deliveryintent.ddls](cds/zjp_i_deliveryintent.ddls), [zjp_i_deliveryintent.bdef](behavior/zjp_i_deliveryintent.bdef) and the `ZBP_I_DELIVERYINTENT` skeleton. **[Phase 5.1](docs/phase-5-1-outbound-foundation.md)'s connectivity half is runtime-verified too** — SAP has called the deployed CAP application over HTTPS with OAuth2 — while its remaining design half is still design: no builder, no mapper, no real HTTP transport, no coordinator and no `sendToSupplier`. That design half prepares the SAP side for direct SAP → CAP HTTP: it reviews connectivity, inventories the nine integration fields on `ZJP_PO_H` and finds none missing but two carrying unusable values — both since fixed in 5.2a — designs the `DeliveryIntent` persistence, since built, designs the outbound DTO mapping, still unbuilt, specifies the transport abstraction, now written as source in 5.2c, and lists the blockers and ADT probes that gate the rest. The released outbound HTTP client API is no longer among them: it was found by probe, not by memory, and the chain that actually worked was not the one this repository had guessed. `sendToSupplier` remains unimplemented and belongs to Phase 5.2f.

The last SAP runtime-verified checkpoint: **[Phase 3.1](docs/phase-3-1-odata-service-exposure.md) is SAP runtime-verified** — the BO is exposed as OData V4 through projection behavior definition [zjp_c_purchaseorder.bdef](behavior/zjp_c_purchaseorder.bdef), service definition `ZJP_UI_PURCHASEORDER` and binding `ZJP_UI_PURCHASEORDER_O4`, with draft, `$expand` and all five bound business actions reachable over HTTP and every Phase 2 rule still enforced by the same handlers. [Phase 3.2](docs/phase-3-2-ui-annotations.md) is SAP runtime-verified on top of that: metadata extensions [zjp_c_purchaseorder.ddlx](cds/zjp_c_purchaseorder.ddlx) and [zjp_c_purchaseorderitem.ddlx](cds/zjp_c_purchaseorderitem.ddlx) at layer `#CUSTOMER` drive a Fiori Elements List Report with a four-field Filter Bar, and an Object Page with header info, a ten-field General Information facet and an Items table over `_Items`. Phase 2 remains complete, SAP runtime-verified through [Phase 2.7E](docs/phase-2-7e-purchase-order-number.md). Root actions `submit`, `approve` and `reject` carry business `Status` from `DRAFT` to `SUBMITTED` and then to `APPROVED` or `REJECTED`, rejection requiring a reason and recording `RejectionOrigin = APPROVER`, and the root action `cancel` carries `DRAFT`, `SUBMITTED` or `APPROVED` to the terminal `CANCELLED` while refusing `REJECTED`, `CANCELLED` and the transient `INITIAL`. RAP prechecks enforce the invariant that commercial content is editable only while `Status` is `DRAFT`, covering root updates, item updates, create-by-association and [Phase 2.6](docs/phase-2-6-technical-draft.md) `removeItem`, for active and technical draft instances; `CANCELLED` falls under that invariant with no new precheck code. RAP technical draft identity remains distinct from business `Status = 'DRAFT'`, and authorization is still the permissive study stub. [Phase 2.7D-2](docs/phase-2-7d-1-cancel-action.md#phase-27d-2-root-delete-narrowed-to-draft-runtime-verified) restricts physical root `DELETE` to `DRAFT` through `delete ( precheck )`, so terminal orders survive as deliberate test residue and technical draft `Discard` is unaffected. [Phase 2.7E](docs/phase-2-7e-purchase-order-number.md) allocates `PurchaseOrderNumber` on a successful `submit` as `PO` plus eight digits from number range object `ZJP_PO` interval `01` — on `DRAFT` → `SUBMITTED` only, never on create/save and never through a determination, so an order cancelled straight from `DRAFT` carries no number. Both are SAP runtime-verified and they close Phase 2. Outside Phase 2: the `APPROVED` cancellation delivery-request guard, which is unreachable here and belongs with `DeliveryIntent` in Phase 5, and `sendToSupplier`, also Phase 5. The OI-02 number-range investigation is finished: a released mechanism exists on the target, so `PurchaseOrderNumber` was implemented inside Phase 2 rather than deferred, and no destination phase was ever named for it.
